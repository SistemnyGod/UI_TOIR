# Передача незаконченного обхода коллеге по смене (2026-10-19)

Сотрудник передаёт начатый или приостановленный обход другому сотруднику смены.
Точки, которые он уже заполнил, остаются за ним в отчёте; оставшиеся выполняет новый исполнитель.

Не путать с существующими действиями:
- «Сменить маршрут» (`/switch`, `switchPatrolAssignment`) — один сотрудник переключается между своими обходами;
- `handoffPatrolAssignment` — передача обхода диспетчеру (`needsDispatcherDecision`).

## Сценарии

| | Тот же телефон (общий аккаунт смены) | Другой телефон |
|---|---|---|
| Кому можно передать | Сотруднику, привязанному к этому аккаунту | Сотруднику, привязанному к другому активному аккаунту |
| Нужна связь | Нет, работает офлайн | Да, список коллег приходит с сервера; команда всё равно идёт через очередь |
| Статус после передачи | Не меняется (`inProgress` остаётся `inProgress`) | `paused`; коллега продолжает на своём телефоне |
| Что с обходом на этом телефоне | Продолжается под новым исполнителем | После подтверждения сервера удаляется с телефона |
| Заполненные точки | Остаются на телефоне, войдут в отчёт | Уходят на сервер в команде передачи вместе с фото |

## Мобильное приложение

- Действие «Передать коллеге» в меню обхода (`src/features/patrol/patrolActionMenu.ts`) для статусов `inProgress` и `paused`.
  По умолчанию открывает `/patrol/assignment/[id]/handover`; экран может передать `onHandover: null`, чтобы скрыть действие.
- Экран `PatrolHandoverScreen`:
  - показывает текущего исполнителя и число заполненных точек;
  - список коллег: сначала этого телефона, затем других телефонов;
  - офлайн доступны только коллеги этого телефона;
  - на этом же телефоне нельзя выбрать коллегу, у которого уже идёт другой обход (для обхода в `inProgress`).
- `transferAssignmentLocally` в одной транзакции:
  - меняет `patrol_assignments.employee_id` и исполнителя в доске заявок;
  - для другого телефона ставит обход в `paused`;
  - кладёт в outbox команду `transferPatrolAssignment`.
- Порядок: команда попадает в агрегат `patrolAssignment:{id}` и отправляется после уже поставленных команд точек.
  Фото из `pointResults` загружаются до отправки (`uploadCandidatePolicy`).
- Ответ сервера (`patrolTransferSync.applyPatrolTransferResponseInTransaction`):
  - **принято, тот же телефон:** обновляется ревизия;
  - **принято, другой телефон:** удаляются обход, его точки, строка доски заявок и автоотправка; файлы остаются до штатной очистки;
  - **отклонено или конфликт:** исполнитель и статус возвращаются прежние.
    Обход не переводится в `needsDispatcherDecision`; запись конфликта остаётся в очереди отправки.
- Пока передача не отправлена, bootstrap не возвращает прежнего исполнителя (`employee_id` сохраняется при незавершённой команде).
- Bootstrap (`applyPatrolTransferBootstrapInTransaction`):
  - запоминает `patrolTransfer` в новой таблице `patrol_transfer_state`;
  - записывает `transferredPointResults` в `point_results` со `sync_status = 'transferred'` и без фото, если по точке ещё нет результата.
    Благодаря этому принявший телефон видит выполненные точки и может отправить отчёт.

## Контракт

### Bootstrap

- `patrolTransfer: true` — сервер принимает команду и отдаёт список коллег.
- `assignments[].transferredPointResults[]` — точки, заполненные на другом аккаунте до передачи:
  `pointId, status, comment, issueTypeId, confirmationType, manualReason, completedAtLocal, performerEmployeeId, performerName, photoCount`.

### `GET /api/v1/mobile/patrol/transfer-candidates`

Возвращает все сотрудники, привязанные к активным мобильным аккаунтам.
Поля: `employeeId, fullName, position, department, sameAccount, hasPatrolInProgress`.

### Команда outbox `transferPatrolAssignment`

`entityType = patrolAssignment`, `entityLocalId = assignmentId`. Payload:

```json
{
  "assignmentId": "…", "requestId": "…",
  "fromEmployeeId": "…", "fromEmployeeName": "…",
  "toEmployeeId": "…", "toEmployeeName": "…",
  "mode": "sameDevice | otherDevice",
  "statusBefore": "inProgress | paused",
  "reason": "до 500 символов, необязательно",
  "transferredAtLocal": "ISO",
  "pointResults": ["в формате completePatrolAssignment.pointResults: заполненные точки"],
  "dependencies": []
}
```

Режим и итоговый статус сервер определяет сам: передача на тот же телефон, если `toEmployeeId` привязан к аккаунту отправителя.

Ответы:
- `accepted`: `serverEntityId = assignmentId`, `serverRevision` — новая `LockVersion`. Повтор той же `clientOperationId` возвращает `duplicate`.
- `conflict`:
  - `transferPerformerChanged` — исполнитель уже не `fromEmployeeId`, или он не привязан к аккаунту;
  - `transferTargetUnavailable` — у коллеги нет активного мобильного аккаунта;
  - `transferTargetBusy` — коллега на этом же телефоне уже выполняет другой обход;
  - `assignmentClosed`, `assignmentNeedsDecision`, `assignmentNotInProgress`.
- `rejected`:
  - `transferSameEmployee`;
  - `transferPhotosMissing` — при передаче на другой телефон фото заполненных точек ещё не загружены;
  - неполный payload, точка не из маршрута, незавершённый статус точки.

## Сервер

- Таблица `patrol_assignment_transfers` (миграция `20261019114654_PatrolAssignmentTransfers`). Строка пишется при каждой принятой передаче и не меняется.
  Поля: от кого и кому, аккаунт, режим, причина, статус до и после, JSON заполненных точек, число точек.
- В истории заявки пишется событие `performerTransferred`.
- Для другого телефона на каждый аккаунт коллеги создаётся уведомление `patrolTransferred`.
- Совмещение с другими действиями:
  - передача берёт ту же блокировку `patrol-start:{employeeId}`, что и старт, продолжение и переключение;
  - ставить обход на паузу до смены исполнителя нужно из-за уникального индекса «один обход в работе на сотрудника».
- При завершении отчёта (`completePatrolAssignment` и применение позднего отчёта):
  - **авторство:** каждая точка из передачи записывается на того, кто передал её первым (`PatrolResult.EmployeeId/EmployeeName`), остальные — на текущего исполнителя;
  - **данные точек с другого аккаунта:** берутся из передачи, а не из отчёта принявшего телефона. Его копия без фото; фото ищутся в файлах исходного аккаунта;
  - **проверка дублей отчёта** сравнивает только присланные точки, как раньше.
- Журнал для диспетчера: `GET /api/v1/patrol-transfers?assignmentId=&limit=` (право `requests.read`).

## Веб-панель

Вкладка «Передачи обходов» в «Результатах обходов» (`PatrolTransfersView`).
Показывает когда, заявку и маршрут, кто передал (и с какого аккаунта), кому, способ, число выполненных точек, причину и текущий статус.
Авторство точек видно в карточке результата обхода, поле сотрудника по каждой точке.

## Ограничения

- Пока передача на другой телефон не отправлена, обход на исходном телефоне стоит на паузе с новым исполнителем.
  Если там нажать «Продолжить», команда продолжения уйдёт после передачи и будет отклонена сервером.
- На принявшем телефоне точки из передачи можно открыть и изменить. Сервер всё равно возьмёт версию из передачи.
  Имя первого исполнителя на телефоне у точки не показывается.
- Передать не начатый (`accepted`) обход нельзя: для этого есть выбор исполнителя при принятии заявки.
