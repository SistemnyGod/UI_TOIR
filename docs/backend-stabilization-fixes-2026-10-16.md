# Исправление снимков маршрутов операций ЭМУ и правил фотографии

Дата: 16 октября 2026 года. Выполнен согласованный план в рабочей копии основного проекта `Proekt obhod`.

Исправлены согласованность снимков маршрутов, конкурентное завершение ЭМУ, сохранение интервалов и проверка времени участников. Обязательность фотографии снята из действующих сценариев; старые поля сохранены для совместимости. Рабочие API/web/worker и БД не обновлялись. APK не собирался и не устанавливался.

## Снимки маршрутов

- Две реализации создания снимка объединены в [PatrolRouteRevisionStore](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/PatrolRouteRevisionStore.cs>).
- Создание заявки, отдельного назначения и мобильное принятие старой заявки используют общий путь. Перед чтением актуального маршрута захватывается блокировка его строки `FOR UPDATE`; блокировка удерживается до фиксации назначения и снимка.
- Редактирование, архивирование, добавление/изменение/удаление и перестановка точек используют ту же блокировку и транзакцию. Другие маршруты этой блокировкой не сериализуются.
- После ожидания блокировки маршрут перечитывается. Для редактирования точки обновляются одним запросом с сохранением отслеживаемых экземпляров сущностей; прежние прочитанные значения не подменяют актуальное состояние.
- Одновременные назначения одной версии используют один снимок. Существующие ревизии и их точки не переписываются.

Проверены оба порядка гонки: редактирование первым — назначение получает целиком новую версию; создание снимка первым — сохраняется целиком старая версия, а редактирование ждёт её фиксации. Также проверены два параллельных назначения и сохранение разных версий одного маршрута в bootstrap.

## Операции ЭМУ

- Пятнадцать команд работ и связанных планов используют [единый механизм транзакций](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Emu/EfEmuService.Mutations.cs>). Он охватывает создание, редактирование, участников, паузу/возобновление, завершение, удаление, перенос и команды планов.
- Сохранены существующие гарантии общей блокировки участия. Та же блокировка применяется к ночному переносу, чтобы он не перезаписывал параллельную правку или завершение.
- `RowVersion` работы и плана настроен как EF concurrency token. Ошибка конкурентной записи переводится в существующий результат с полем `rowVersion`. Чтение карточки для предварительного просмотра/проверки доступа не оставляет в контексте устаревшую отслеживаемую копию.
- Работа, участники, интервалы, связанный план и события аудита фиксируются одной транзакцией. При вызове из мобильной очереди используется savepoint внешней транзакции; внутренняя команда не подтверждает всю очередь самостоятельно.
- При отказе SQL или конфликте частично записанное состояние откатывается. Обработчик мобильной очереди и её квитанции сохранены.
- При завершении проверяется время прихода каждого выбранного участника. Частичное завершение оставляет остальных участников активными. Аналогичная проверка времени применена к паузе и возобновлению.
- Закрытие интервалов осталось одной SQL-операцией для выбранных участников. Проверки уже выполненного ночного переноса собраны одним запросом вместо запроса на каждую работу.

Проверены конкурирующие пары: завершение/завершение, пауза/завершение, добавление участника/завершение, удаление/завершение и ночной перенос/завершение. Два worker не создают два переноса. Искусственный отказ закрытия интервалов откатывает работу, участников, план и аудит как в самостоятельной, так и во внешней мобильной транзакции.

Существующие столбцы и таблицы достаточны. Обновлены EF-метаданные и model snapshot; отдельный тест подтверждает отсутствие ожидающих изменений модели. Новая миграция схемы не добавлена, к рабочей БД миграции не применялись.

## Фотографии добровольные

По уточнению пользователя прежний пункт аудита о потере `RequiresPhoto=true` не должен исправляться включением обязательности. Устранено рассогласование оставшихся форм, проверок и старых данных:

- Удалён переключатель требования фото в создании и редактировании точки. Веб больше не блокирует завершение из-за отсутствующего фото и не показывает метку обязательности.
- Сервер не требует фото для исправности, неисправности или пропуска. Требования к статусам, комментариям и типу неисправности сохранены.
- Поле `requiresPhoto` осталось в совместимых контрактах и отдаётся как `false`, включая старые снимки в bootstrap. Веб также нормализует старое значение при чтении и отправке формы.
- Мобильная политика, форма осмотра и проверка готовности не требуют фото даже при `true`, уже сохранённом в старом офлайн-назначении.
- Если пользователь приложил файл, сохраняются проверки размера, типа/хеша и факта загрузки. Отчёт со ссылкой на несуществующее вложение отклоняется.
- Исторические фотографии, сохранённые флаги и содержимое прежних ревизий не изменяются в БД. Старые CSV-столбцы сохранены, эффективный статус фото больше не становится `missing` из-за прежнего флага.

Проверен мобильный серверный цикл со старым флагом: bootstrap → принятие → начало → отказ незагруженного вложения → принятие неисправности без фото → повтор операции без второго результата. Дополнительно проверены форма мобильного осмотра и локальная готовность старого офлайн-назначения.

Для уже установленного APK сервер не может изменить исполняемую клиентскую проверку или гарантированно заменить неизменяемый локальный снимок. Чтобы снятие обязательности действовало и в таких офлайн-назначениях, потребуется выпуск обновлённого APK и приёмка на телефоне. Стирать локальные данные для этого не требуется.

## Оптимизация отчёта

[Сохранение результатов точек](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.Results.cs>) получает существующие ID точек одним запросом и проверяет их через `HashSet`. Для маршрута на 54 точки тест подтвердил одну пакетную выборку и отсутствие 54 прежних поштучных `SELECT EXISTS`.

Проверка существования ссылок сохранена: точка старого снимка может быть удалена из текущего справочника, но её результат остаётся доступен по сохранённым данным. Ускорение в миллисекундах на рабочей нагрузке не измерялось.
