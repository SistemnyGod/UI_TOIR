# Пилот документов выдачи СИЗ

## Флаг и права

По умолчанию конструктор выключен:

```dotenv
PPE_ISSUE_DOCUMENTS_ENABLED=false
```

Compose передаёт значение в API как `Features__PpeIssueDocuments`. Флаг
управляет доступностью endpoints документов выдачи; он не управляет миграциями
БД и не является переключателем deployment.

Для работы нужны:

- `inventory.view` — просмотр;
- `inventory.ppe.manage` — создание, изменение и подтверждение документа;
- `inventory.reports.export` — скачивание печатных форм;
- `inventory.ppe.norms.manage` — утверждение применимости нормы и соответствия
  номенклатуры.

## Запуск пилота

1. Использовать тестовый или staging-контур, не production. Перед началом
   владелец пилота подтверждает сотрудников, период и ответственного за
   остановку пилота.
2. Для API задать флаг в отдельном env-файле пилота, например
   `.env.ppe-pilot`:

   ```dotenv
   PPE_ISSUE_DOCUMENTS_ENABLED=true
   ```

3. Запустить печать только явным профилем:

   ```powershell
   # Из infra/docker; .env относится только к выбранному тестовому контуру.
   docker compose --env-file .env --env-file .env.ppe-pilot --profile app --profile ppe-printing up -d api gotenberg
   ```

   При выключенном флаге и без `--profile ppe-printing` контейнер Gotenberg не
   запускается. Лимиты Gotenberg: память `1G`, CPU `2.0`.
4. Выдать права только назначенным пользователям. Перед подтверждением
   проверить сотрудника, норму, номенклатуру, количество, цену и даты.
5. После подтверждения факт выдачи нельзя редактировать или архивировать через
   legacy API. Возврат, списание и утеря остаются разрешёнными lifecycle-
   операциями.
6. Для остановки пилота задать `PPE_ISSUE_DOCUMENTS_ENABLED=false`,
   перезапустить API и при необходимости остановить профиль печати:

   ```powershell
   docker compose --profile ppe-printing stop gotenberg
   ```

Начальное approval пилота: владелец контура подтверждает включение флага и
назначает пользователей с указанными правами. Дополнительный письменный
процесс здесь не требуется.

## Миграции и production

В текущем Compose API запускается после отдельного сервиса `migrate`, который
стартует `Patrol360.Api.dll --migrate` и применяет EF migrations. Это может
произойти даже при `PPE_ISSUE_DOCUMENTS_ENABLED=false`. Поэтому перед запуском
проверяйте фактическую команду deployment и состояние БД отдельно от флага.

Флаг не публикует документы автоматически, не включает production сам по себе
и не создаёт migration/backfill. Production-включение и любые миграции должны
быть отдельными одобренными действиями; этот runbook их не авторизует.

Без отдельного approval production-значение остаётся
`PPE_ISSUE_DOCUMENTS_ENABLED=false`.

## Подготовка норм

Импорт создаёт черновики редакций, а не разрешение выдавать товары. До публикации
ответственный подтверждает подразделение и отдельные должности, проверяет
единицы и периоды, затем утверждает соответствия товаров с основанием проверки
защитных свойств. Категория не означает взаимозаменяемость: альтернативы
задаются отдельной группой. Право управления нормами автоматически получает
только администратор; ответственному за ОТ его назначают через роли.

Старые соответствия не становятся утверждёнными автоматически. Связь требований
между редакциями подтверждается отдельно. Неподтверждённая история отображается
как неизвестная и требует ручного контроля с причиной. В переданном примере
Word должность внутри документа отличается от имени файла; реального сотрудника
нельзя использовать для пилота до уточнения фактической должности.

## Проверка 8 сентября 2026

- На отдельном PostgreSQL применена добавочная миграция `20260908034927_PpeIssueDocuments`.
  Рабочая база не изменялась. Откат пилота выполняется флагом, не удалением новых
  таблиц и не запуском Down после появления документов.
- Реальный Excel: 448 товарных строк, 34 профессиональных блока. Двойной импорт
  создал 68 наборов без перезаписи первой редакции; контрольный замер двух
  импортов составил 511 мс на тестовой базе.
- 11 интеграционных тестов документа проходят, включая одновременное
  подтверждение, идемпотентность, отсутствие складских движений, возврат,
  неизвестную историю и снимки справочников. Дополнительно проходят проверки
  повторного импорта и конкурентной публикации.
- Контрольный сценарий подбора, сохранения и подтверждения одной синтетической
  позиции: 17 SQL-команд, 509–526 мс. Это не нагрузочный тест рабочей базы.
- Многостраничные DOCX с 54 синтетическими позициями открыты в Word и визуально
  проверены через его QA-экспорт: кириллица, повторение заголовков, даты и границы
  строк. Этот экспорт не является производственным PDF-конвертером.
- Реальная проверка Gotenberg пока не выполнена: Docker Registry вернул ошибку
  `HTTP response to HTTPS client` при загрузке образа. Перед включением пилота
  обязательны реальная конвертация, сравнение обеих форм и замер памяти/времени PDF.

Для opt-in проверок используются `PATROL360_RUN_DB_INTEGRATION=true`,
`PATROL360_DB_INTEGRATION_ADMIN_CONNECTION_STRING` (только отдельная тестовая БД),
`PPE_TEST_NORMS_XLSX`, `PPE_TEST_PRINT_OUTPUT` и `PPE_TEST_GOTENBERG_URL`.
API отправляет DOCX в [официальный маршрут LibreOffice Gotenberg](https://gotenberg.dev/docs/convert-with-libreoffice/convert-to-pdf).

Итоговые проверки кода: 34 новых серверных теста СИЗ прошли, одна реальная
проверка Gotenberg пропущена; 70 API unit-тестов прошли. Сборка frontend и
четыре focused unit-теста прошли. Playwright со synthetic API прошёл выбор,
редактирование, повторное открытие и подтверждение; сняты все шаги на ширинах
1365 и 390 пикселей. Это не заменяет браузерную проверку с настоящим API пилота.

Общие проверки проекта не полностью зелёные: полный Vitest показал ошибки вне
нового сценария и был остановлен после зависания; из девяти legacy DB-тестов
восемь прошли, один старый тест печати ожидает нормативное название и количество
в листе подписи, хотя существующий экспорт выводит товар и фактическое количество.
Этот экспорт и тест не менялись в данной работе. Перед production нужен отдельный
прогон общей регрессии. Vite также предупреждает о чанке inventory около 537 кБ
до gzip; нагрузочная проверка рабочей базы и памяти контейнера не выполнялась.
