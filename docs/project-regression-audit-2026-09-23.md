# Аудит текущего проекта — 23 сентября 2026

## Вывод

Базовые сборки и серверные интеграции проходят. Однако текущую рабочую редакцию нельзя считать готовой к выпуску: воспроизведены ошибки определения завершения обхода и подгрузки работ. Зелёный мобильный verify не покрывает эти сочетания событий. Два веб-теста перестали соответствовать изменённому интерфейсу.

Это межмодульный аудит текущей рабочей копии, включая незакоммиченные изменения, а не доказательство отсутствия ошибок во всех ветках проекта. Проверены архитектура и изменения мобильного приложения, серверные контракты и SQL-пагинация, bootstrap, обработка обходов, изменения ЭМУ, СИЗ и веб-панели; выполнены автоматические проверки решения. Ручной полный прогон каждого веб-раздела и проверка каждого исходного файла не выполнялись. Наличие дефекта сейчас не всегда устанавливает коммит, впервые его внесший: для этого нужен отдельный прогон зафиксированного базового состояния.

Код приложения и сервера в рамках аудита не менялся. Добавлен диагностический скрипт `tools/audit-project-regressions-2026-09-23.cjs`.

## Приоритетные проблемы

### 1. P1 — ошибка доставки точки считается завершением обхода

Место: `mobiel proekt/src/services/patrolNavigationService.ts:37–39`; установка ошибки назначения — `src/db/repositories/outboxRepository.ts:2095`.

`getPatrolReportState` считает `syncError`, `authRequired` и `needsDispatcherDecision` доказательствами завершения. Обработчик квитанций может выставить ошибку назначения при отказе команды точки, без команды `completePatrolAssignment` и без локального отчёта. В диагностике `status=syncError`, `local_report_present=0`, команда завершения отсутствует, но функция возвращает `completedLocally=true`.

Последствие: восстановление ведёт на итог, а экран отправки работает как с уже существующим отчётом. Исправление: использовать доказательства завершения и явное переоткрытие, а ошибки доставки хранить и отображать независимо. Закрепить тестами ошибку точки, конфликт точки, незавершённый обход и действительный завершённый отчёт.

### 2. P1 — продолжение работ на сервере становится недоступным

Места: `src/features/emuTask/WorkAccountingScreen.tsx:214,535,663,836`; `src/db/repositories/workTaskRepository.ts:140`.

После локального чтения `taskHasMore` определяется только локальным курсором. Если в кеше ровно 25 строк, но сервер вернул продолжение, `handleLoadMore` выходит до HTTP-запроса. Диагностика фактического обработчика подтверждает ноль запросов.

Дополнительно репозиторий ограничивает общую выборку до применения фильтра сотрудника/раздела: «Мои», «Доступные» и «История» фильтруются в React. Первая локальная страница может состоять целиком из неподходящих записей. Тогда показывается «Работ нет», ручная кнопка подгрузки скрыта; автоматический `onEndReached` не заменяет корректную пагинацию подходящих строк.

Исправление: общий фиксированный контекст фильтра для SQL, кеша и сети; фильтрация до LIMIT. Разделить локальное и серверное продолжение, различать неинициализированный список и конец. Проверить 25 локальных + серверная следующая страница, 200+ работ, первая страница только другого сотрудника, редкие «Доступные».

### 3. P2 — офлайн нельзя дочитать уже сохранённую страницу работ

Место: `WorkAccountingScreen.tsx:540–541`.

Обработчик сначала ждёт `loadMoreWorkItems`, затем читает SQLite. Если сеть недоступна, локальное чтение не выполняется. В диагностике при существующем локальном курсоре и ошибке сети число локальных чтений равно нулю.

Исправление: сначала выдавать сохранённое локальное продолжение; сервер запрашивать отдельно по необходимости. Сетевая ошибка не должна блокировать кеш. Не допускать повторного добавления первой страницы при пустом локальном курсоре.

### 4. P2 — сохранённый диапазон списка сбрасывается при возвращении

Место: `WorkAccountingScreen.tsx:184–224`.

Код читает сохранённый лимит, но циклы дочитывания запрещены условием `!shouldReset`. При возвращении выполняется `reloadLocal(true)`: вместо сохранённых 75 строк загружаются 25, после чего 25 записывается как новый лимит. Это воспроизведено фактической функцией с управляемым хранилищем. Аналогичное условие используется для замечаний.

Исправление: восстанавливать нужный диапазон и при повторном открытии; сбрасывать его только при новом контексте фильтра. Проверить возвращение на экран и сохранение положения прокрутки отдельно на устройстве.

### 5. P2 — восстановительный проход истории не возобновляется с сохранённой страницы

Место: `src/services/workTaskService.ts:68–115`.

При повреждённой границе `recoveryPass=true` существует только в памяти, а курсор принудительно становится null. После обрыва сохранённый курсор игнорируется. В диагностике с реальным SQLite и пересозданием сервиса запросы: первая страница → вторая с ошибкой → снова первая → вторая. Все 115 записей в итоге доступны: потерю 15 записей здесь не заявляем. Старый курсор истории также остаётся прежним после прохода до конца.

Исправление: сохранять режим восстановления и его продолжение; завершение прохода и согласование старого курсора выполнять атомарно. Добавить регрессию повреждённой границы + обрыв + перезапуск, а не только успешный непрерывный проход.

### 6. P2 — жизненный цикл загрузок экрана работ остаётся неполным

Места: `WorkAccountingScreen.tsx:174–277,363–369,518–551`.

По коду: обычный `useEffect` запускает сетевое обновление отдельно от фокусного эффекта; окончание загрузки вызывает `reloadLocal` до проверки `isMounted`; поколение локальной загрузки не инвалидируется при уходе. `handleLoadMore` не проверяет поколение фильтра после ожидания сети. Поэтому задержанный ответ старого фильтра может дописать строки в новый список. События по-прежнему перечитывают работы, замечания, сотрудников и участки вместе.

Это подтверждённые недостающие проверки в коде; отдельное воспроизведение на смонтированном React Native экране в этом аудите не выполнялось. Исправление: один владелец запроса с контекстом аккаунта/контура/фильтра/фокуса, синхронная блокировка подгрузки, проверка после каждого ожидания, адресное чтение по событиям. Добавить управляемые задержки и смену фокуса в тесты экрана.

### 7. P2 — два веб-теста СИЗ больше не проверяют нужное поведение

Место: `apps/web/src/__tests__/ppeIssueDocument.test.ts:66,100`.

Тесты вызывают `selectOptions` для нового input с role=combobox. Оба падают с `Value ... not found in options`. До проверки устаревших ответов норм и запрета изменения при просмотре без прав они не доходят.

Исправление: взаимодействовать с поиском и вариантами выбора как пользователь, затем сохранить прежние проверки гонки и отсутствия PUT. Не удалять тесты и не ослаблять проверки. По этому падению нельзя заключать, что сама выдача СИЗ или проверка прав сломана.

## Сохранение форм и оптимизация: оставшиеся проверки

- Контроллер точки теперь повторно сохраняет изменения, введённые во время записи; существующий тест этого поведения проходит. Старое воспроизведение потери ввода нельзя переносить на текущий код без перепроверки.
- Однако `PointFillScreen.tsx:68–76` не сохраняет отдельное действие повторного перехода после ошибки, а контроллер возвращает Promise до внешнего dispatch. Требование атомарного завершения контроллера вместе с навигацией реализовано не полностью. Нужны тесты ошибки/повтора, ввода на границе завершения, камеры и системной кнопки «Назад». Потерю текста на телефоне в этом аудите не подтверждали.
- `refreshWorkItemsHead` всё ещё читает весь локальный набор работ для вычисления границы, включая преобразование карточек. Перейти на компактные ключи ID/ревизия нужного фильтра.
- `isReportFullyDelivered` запрашивает файлы по одному; экран и навигация повторяют часть чтений. Выделить согласованное чтение отчёта и пакетную проверку файлов. Ускорение пока не измерено.
- События со списками ID должны вести к адресному SQLite-чтению, а не обновлению всех справочников. Новые индексы выбирать после EXPLAIN QUERY PLAN и замеров.
- Веб-сборка предупреждает о крупном inventory-чанке (~584 КБ до gzip). Это направление для замеров и разделения загрузки, не блокирующая ошибка.

## Порядок исправления и приёмки

1. Превратить воспроизведения в регрессионные тесты ожидаемого поведения. Исправить определение локального отчёта.
2. Исправить единую пагинацию работ: SQL-фильтры, независимое локальное/серверное продолжение, офлайн-чтение, сохранение диапазона.
3. Сохранять восстановительный режим истории; добавить обрыв и перезапуск в тесты.
4. Объединить управление загрузками экрана; проверить старые ответы, смену сотрудника/аккаунта/фильтра и скрытый экран. Завершить сценарий повторного сохранения формы.
5. Обновить два веб-теста под combobox, выполнить все проверки повторно.
6. Снять сравнимые замеры и провести пилот на двух телефонах: А не закончил → Б выбрал → завершил офлайн → отправил → получил квитанцию → список → перезапуск не возвращает А.

Полноценное разрешение конфликта отмены с офлайн-отчётом и история переписки остаются за пределами последних согласованных этапов. Их отсутствие не следует выдавать за вновь возникшую регрессию.
