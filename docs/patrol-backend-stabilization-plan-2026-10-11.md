# План стабилизации бэкенда модуля «Обходы»

Дата: 11 октября 2026 года.

## Цель и границы

Стабилизировать серверный цикл: **создание заявки → получение телефоном → принятие и начало обхода → фиксация точек и вложений → отправка отчёта → подтверждение сервера → просмотр результата в вебе**.

Работу ограничить модулем «Обходы» и необходимыми общими зависимостями: мобильная авторизация, bootstrap, outbox, файлы, уведомления и готовность API. СИЗ, складской учёт, бизнес-логика ЭМУ и PERCo не входят в этап. Общие компоненты проверять также на совместимость с их существующими потребителями.

Оставить модуль в существующем монолите. Объединять правила обхода за действующими application-интерфейсами; контроллеры веба и мобильного приложения остаются адаптерами к этим правилам. Новое разбиение на сервисы или массовое переписывание проекта для достижения цели не требуется.

Это план, подготовленный по текущему коду и предыдущим отчётам. На данном этапе прикладной код, рабочие сервисы и БД не изменялись; новый прогон тестов и повторная диагностика рабочего сервера не выполнялись.

## Что уже есть

- [Заявки](../apps/api/Controllers/PatrolRequestsController.cs) и [назначения](../apps/api/Controllers/AssignmentsController.cs) имеют отдельные веб-endpoints; сохранение заявки создаёт назначение, ревизию маршрута и запись уведомления.
- [Мобильный API v1](../apps/api/Controllers/MobileController.cs) предоставляет авторизацию, bootstrap, outbox, проверку результата операции, файлы, уведомления и историю отчётов. [API v2](../apps/api/Controllers/MobileV2Controller.cs) обслуживает мобильные работы; этот общий контракт сохраняется.
- [Outbox](../libs/infrastructure/Persistence/MobileApp/EfMobileAppService.Outbox.Patrol.cs) уже содержит квитанции операций, транзакции, блокировку по аккаунту/ID операции и блокировки назначений. [Завершение обхода](../libs/infrastructure/Persistence/MobileApp/EfMobileAppService.Outbox.Patrol.Completion.cs) проверяет точки, фотографии и версии.
- [Мобильный клиент](../mobiel%20proekt/src/api/mobileApi.ts) строго проверяет полноту ответа outbox, идентификаторы и статусы. [Схемы клиента](../mobiel%20proekt/src/api/schemas.ts) отклоняют неизвестные статусы. Локальная очередь сохраняет данные до серверного подтверждения.
- Существуют отдельный мигратор, проверка готовности БД/файлового хранилища, постоянное хранилище ключей Data Protection и worker push-доставки.
- Исправления ревизий новых назначений и конкурентного refresh уже подготовлены и проверены локально: [отчёт 11 октября](./frontend-backend-stability-fixes-2026-10-11.md). Их повторная реализация не нужна; требуется проверить выпуск и полный HTTP-сценарий.

Последний аудит показывал расхождение рабочей копии и работающих образов, а также неприменённые миграции push-квитанций и сортировки заявок. Это состояние нужно перепроверить: сохранённый отчёт не является текущей диагностикой сервера.

## Правила совместимости

1. Сохранить используемые мобильными версиями URL, имена и типы полей, обязательность/nullability, значения статусов и коды причин. Сначала зафиксировать реально установленные версии APK и их протоколы.
2. Не вводить новые обязательные поля, новые значения существующих enum или другую трактовку `accepted`, `duplicate`, `retryLater`, `rejected`, `conflict` в прежнем API. Дополнительные данные — только необязательные и проверенные схемами поддерживаемых клиентов; изменение семантики требует версии/согласования возможностей.
3. На каждую корректную команду outbox возвращать согласованную квитанцию. `accepted` означает зафиксированные в БД изменения. Ошибки сети/БД не маскировать успешной отправкой.
4. Повтор после потерянного ответа использует исходный `clientOperationId`. Он не создаёт ещё один результат. ID другого аккаунта не позволяет читать чужую квитанцию или файл.
5. Сохранить действующие сценарии офлайна, смены владельца, отмены, паузы, передачи и диспетчерского решения. Удаление приложения/очистка локальных данных не являются способом восстановления обмена.
6. Доставка заявки через bootstrap работает независимо от FCM. Ответ FCM об успешной отправке не равен получению уведомления телефоном или принятию заявки сотрудником.
7. Сохранить исторические результаты, вложения и снимки маршрутов. Не подменять неизвестные исторические ревизии текущим маршрутом и не выполнять автоматический откат схемы с удалением данных.

## Порядок работ

### 0. Зафиксировать рабочее состояние и воспроизводимый стенд — P0

- Сверить версии API/web/worker, установленных APK, адрес сервера, `contourId`, настройки времени, прокси и миграции. Записывать метаданные без секретов.
- Отделить предназначенные для выпуска изменения «Обходов» от остальных незавершённых изменений рабочей копии. Собирать определённую ревизию и проверять соответствующий ей набор миграций.
- Подготовить изолированный PostgreSQL: синтетические данные для конкурентных тестов и, при необходимости, защищённую копию рабочей БД для воспроизведения исторических состояний. Проверить восстановление резервной копии; отключить push во внешний контур, PERCo и прочие рабочие интеграции на стенде.
- Подготовить двух сотрудников, два мобильных аккаунта/устройства, обычный и изменяемый маршрут, тестовые заявки и медиа. Зафиксировать исходные результаты тестов и измерения.

**Выход:** можно повторить отказ и сквозной обмен без воздействия на рабочие данные. Известно, какие версии клиентов требуется поддерживать.

### 1. Зафиксировать совместимость HTTP и мобильного протокола — P0

- Составить таблицу фактически используемых endpoints и команд: создание заявки, bootstrap, accept/start/scan/mark/complete, files, receipt lookup, reports, notifications, login/refresh.
- Для каждого проверить авторизацию, владельца, `contourId`, JSON, даты/часовой пояс, nullability, статусы и формат ошибок. Отдельно проверить пустой/частичный/невалидный ответ и повтор ID внутри одного пакета.
- Добавить сквозные HTTP-тесты API с PostgreSQL. Реальные JSON-ответы проверять действующими мобильными схемами, включая обязательные поля всех квитанций.
- Закрепить базовый сценарий «заявка создана в вебе → попала в bootstrap нужного аккаунта → принята → завершена → результат читается в вебе и на телефоне». Проверить старые поддерживаемые и текущую версии клиента.
- Составить единую таблицу переходов заявки/назначения и отобразить её в веб-, мобильных и серверных тестах. Существующие server state machine и status mapper использовать как основу, а не создавать параллельный набор статусов.

**Выход:** защищён текущий протокол. Любой несовместимый ответ или изменение поведения обнаруживается до выпуска.

### 2. Стабилизировать создание и получение заявок — P0

- Проверить атомарность заявки, назначения, ревизии маршрута и уведомления во всех путях создания, включая плановый обход. Ошибка сохранения не оставляет половину операции.
- Проверить привязки сотрудников, блокировки аккаунта, видимость заявок и фильтрацию завершённых/отменённых записей. Заявки не исчезают из-за изменения даты, смены, часового пояса или обновления аккаунта.
- Сохранить согласованную сортировку списков заявок: новые сверху; порядок плановых слотов проверять отдельно по плановому времени. Различать дату создания заявки, плановый старт и время завершения.
- Проверить повтор создания после потерянного ответа и двойное нажатие диспетчера. Если отсутствует защита нужного пути — добавить совместимый необязательный ID и проверку содержимого; бизнес-совпадение сотрудника/маршрута/времени само по себе не запрещает две действительно разные заявки.
- Проверить bootstrap при отказе push, истёкшем access-токене, восстановлении Wi-Fi и перезапуске API. Стабильный cursor должен меняться при изменении существенных данных, сохраняя текущую семантику полного снимка.
- Отдельно воспроизвести изменение маршрута после выдачи назначения: телефон с сохранённым обходом, телефон с первым получением после изменения, два назначения с разными ревизиями одного маршрута. Сервер хранит ревизию назначения, а текущий bootstrap формирует каталог из актуальных маршрутов. Нужно доказать согласованность полного обмена; считать это подтверждённой новой ошибкой только после воспроизведения. Решение не должно подменять старый снимок или требовать неподдерживаемых полей от установленного APK.

**Выход:** новая заявка доступна правильному телефону через API без зависимости от push. Назначение можно выполнить по достоверному выданному набору точек.

### 3. Стабилизировать приём отчётов, медиа и квитанции — P0

- Проверить все команды обхода: зависимости, ожидаемую версию, порядок выполнения, повтор, повтор с изменённым содержимым и смену аккаунта.
- Зафиксировать единые границы транзакции для результата, точек, статусов заявки/назначения, истории, ссылок на файлы и квитанции. Потеря ответа после commit должна восстанавливаться чтением квитанции.
- Проверить гонки: два завершения с одинаковыми и разными ID, завершение против отмены, старт с двух устройств, переключение/передача против завершения. Общий порядок блокировок должен предотвращать дубли и взаимные блокировки.
- Проверить пакет с частично выполненными командами и остановку API посередине. Успешные команды не выполняются второй раз; временные ошибки допускают безопасный повтор; постоянный бизнес-конфликт возвращается действующим понятным статусом/кодом.
- Проверить файлы: владелец/назначение/точка, `clientFileId`, размер, MIME и фактическое содержимое, хеш, повтор загрузки, повреждённая/незавершённая загрузка, отсутствие файла на диске при наличии строки БД. Отчёт не принимается как полный, если обязательное медиа отсутствует.
- Для согласования БД и файлов использовать устойчивые состояния загрузки/подтверждения и безопасную очистку только доказанных сирот. Не удалять медиа незавершённых отчётов.
- Проверить HTTP-ошибки и rate limit вместе с мобильным retry: 401, 403, 409, 413, 429, 5xx/тайм-аут. Не менять коды произвольно и не превращать временный инфраструктурный отказ в окончательное отклонение отчёта.

**Выход:** сервер хранит один корректный результат и все его вложения. После обрыва ответа телефон получает достоверное подтверждение без дубля или потери локального отчёта.

### 4. Проверить уведомления, авторизацию и диагностику доставки — P1

- Проверить постоянство Data Protection-ключей между перезапусками/экземплярами API. Повтор refresh не должен зависеть от случайного нового набора ключей.
- Проверить отзыв устройства/аккаунта, параллельный refresh, смену исполнителя и получение квитанции после повторного входа в тот же аккаунт. Чужой аккаунт не получает прежние данные.
- Проверить новую push-миграцию и существующий механизм доставки: два worker, перезапуск после claim, частичный отказ устройств, недействительный токен и лимит попыток. Успешно отправленным устройствам повтор не выполняется.
- Различать в диагностике сохранение заявки, выдачу через bootstrap, отправку провайдеру, чтение уведомления и принятие сотрудником. Не выдавать серверное «отправлено» за подтверждение телефона.
- Добавить или унифицировать журналы по `requestId`, `assignmentId`, `clientOperationId`, аккаунту и устройству: время, этап, итог, код причины, повтор/длительность. Не журналировать пароли, access/refresh-токены, содержимое файлов и полный чувствительный payload.
- Проверить `/health/ready` и мобильный `/health`: недоступность БД, несоответствие миграций и отказ записи файлов дают честную недоступность. Отказ FCM не должен останавливать приём отчётов и выдачу bootstrap.

**Выход:** для конкретной заявки/отчёта можно определить последний подтверждённый сервером этап и причину задержки. Перезапуск сохраняет сеансы, квитанции и очереди.

### 5. Провести постепенный рефакторинг и измеряемую оптимизацию — P1/P2

- По сквозным тестам выявить дубли правил между `EfPatrolStore.Assignments`, мобильными обработчиками и state machine. Выделять общие переходы, проверки маршрута/владельца, сохранение результата и формирование снимка по одному сценарию за изменение.
- У контроллеров оставить HTTP, права и отображение ошибок; у application-сценариев — оркестрацию; у persistence — запросы, блокировки и транзакции. Сохранить существующие интерфейсы/адаптеры, пока их потребители не переведены и проверены.
- Сохранить границу мобильного транспорта: общий outbox может обслуживать ЭМУ, но правила обхода не должны зависеть от операций ЭМУ. Изменение общей оболочки требует проверок обоих потребителей без переделки бизнес-логики ЭМУ.
- Измерить число SQL-запросов, время и размер bootstrap, выборок заявок/результатов, ожидания блокировок, приём outbox и загрузку файлов на реалистичных объёмах и параллельных устройствах.
- Исправлять доказанные N+1, лишние `Include`/материализацию и повторные сохранения. Индексы добавлять после `EXPLAIN (ANALYZE, BUFFERS)` по фактическим фильтрам/сортировке; сравнивать измерения до и после.
- Не обрезать полный bootstrap произвольным `Take`: телефон может трактовать отсутствие записи как изменение состояния. Новая пагинация/дельта требует отдельной проверки протокола и восстановления локальных данных.
- Легаси удалять только после проверки маршрутов вызова, установленных APK и истории. Старый endpoint, alias или формат payload может быть необходимым адаптером совместимости. Отдельно проверить жёстко заданные пилотные маршруты и неактуальные доменные модели.

**Выход:** правила обхода сосредоточены в одном логическом модуле, дубли уменьшены, измерения улучшились, сквозные сценарии и старые клиенты работают как раньше.

### 6. Приёмка и выпуск — P0 для завершения этапа

- Выполнить контрактные, API, PostgreSQL и конкурентные тесты, проверки миграции/восстановления, мобильной синхронизации и смежных потребителей общих компонентов. Старые успешные тесты не заменяют новую сквозную приёмку.
- На реальном телефоне провести контролируемый тест: создать заявку, принять, отключить Wi-Fi, заполнить точки/фото, завершить, восстановить Wi-Fi, проверить результат/вложения в вебе. Повторить потерю ответа и перезапуск приложения/API.
- Перед выпуском сделать и проверить свежую резервную копию БД; отдельно сохранить файловое хранилище и ключи, необходимые для полного восстановления. Сверить все миграции с конкретным образом, не применять случайно изменения из других незавершённых веток.
- Выпустить согласованные API и worker после мигратора и проверки готовности; веб обновлять, если менялся его адаптер обмена. Начать с контрольного аккаунта, затем расширить использование после проверки цепочки и журналов.
- Если выпуск требует изменения поведения мобильного протокола, сначала обеспечить совместимый серверный путь и согласованную поставку APK. Не объявлять совместимость только по номеру API или успешной сборке.
- При сбое остановить расширение выпуска, сохранить данные и журналы, выбрать совместимую прежнюю версию или исправление вперёд. Откат приложения допустим только при совместимости с текущей схемой; новые таблицы, результаты и квитанции не удалять.

**Выход:** на рабочем сервере поддерживаемый APK получает заявку и сервер принимает её отчёт с фотографиями. Зафиксированы версии, результаты приёмки и безопасный способ восстановления.

## Обязательные сценарии приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Заявка без доступного push-провайдера | Получена телефоном через bootstrap; отказ push виден отдельно |
| Заявка для другого сотрудника/аккаунта | Не раскрывается и не может быть принята посторонним |
| Два устройства принимают/начинают обход одновременно | Согласованный результат без двух активных обходов вопреки действующим правилам |
| Изменение маршрута после назначения | Достоверный снимок и одинаковые правила на телефоне и сервере |
| Обход полностью заполнен офлайн | Локальные данные сохраняются; после восстановления сети отчёт принят |
| Фото ещё не загружено или хеш/содержимое неверны | Полный отчёт не подтверждается; доступно безопасное исправление/повтор |
| Ответ после commit потерян | Повтор/чтение квитанции подтверждает один исходный результат |
| Разные ID одновременно завершают одно назначение | Не создают два одинаковых бизнес-факта |
| Диспетчер отменяет начатый обход | Выполняется согласованная существующая политика; локальная работа не исчезает молча |
| Перезапуск API/worker и повторный вход | Сохраняются документы, файлы, ключи и возможность сверить очередь |
| Неизвестный контур, аккаунт или невалидный payload | Понятный совместимый отказ; чужие данные не меняются |
| Старый поддерживаемый APK с новой версией API | Контракты и полный цикл подтверждены тестом |

Выпуск считается завершённым после рабочей приёмки обмена, а не после одного рефакторинга или прохождения unit-тестов. Сначала выполнять этапы 0–3, затем диагностику/рефакторинг/оптимизацию под защитой этих проверок.
