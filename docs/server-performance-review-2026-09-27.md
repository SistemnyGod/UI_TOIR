# Ревью потребления памяти и CPU сервера

Дата: 27 сентября 2026 года. Часовой пояс: Екатеринбург, UTC+5.

Главный вывод: в измеренный спокойный период высокая занятость памяти компьютера не объясняется только Patrol360. API, worker и его PostgreSQL вместе занимают около 580 МиБ. Значительно больше занимает память ядра Windows: около 6,50 ГиБ nonpaged pool, из них 3,33 ГиБ у тега NVRM. Высокая длительная загрузка CPU в этот период не воспроизведена.

Есть подтверждённые возможности сократить постоянную память вспомогательных служб примерно на 286 МиБ по текущим контейнерным показателям, уменьшить повторные SQL-запросы, фоновые обновления браузера и проверки готовности. Они полезны, но не обещают устранить многогигабайтный расход ядра.

## Метод и границы

- Прочитаны конфигурация Docker, worker, API readiness, хранение файлов, пагинация работ, фоновые операции ЭМУ и PERCo, кеш печати и обновления веб-панели.
- Сделаны 8 последовательных снимков Docker и процессов Windows, 17:09:21–17:10:47. Между измерениями ожидание 10 секунд; сам сбор также занимает время. Для вывода об обычной нагрузке использована эта серия, а не предварительная серия с диагностическим вызовом RabbitMQ.
- Статистика PostgreSQL снята в 17:07:40 и 17:14:55, интервал около 436 секунд. Запросы выполнялись в READ ONLY с ограничением времени. Проверен план ограниченного SELECT шаблона смены.
- Прочитаны агрегаты журнала PERCo за сутки и HTTP-прокси за час. В часовой выборке 359 readiness-запросов и 10 прикладных запросов; она не представляет рабочий пик.
- Память ядра прочитана через счётчики Windows и единичный снимок SystemPoolTagInformation. Трассировка и Driver Verifier не включались.
- На момент измерения 21 работающий контейнер, включая другой проект WhisperX и две тестовые БД. Код другого проекта не проверялся.
- Локальный HEAD: `367fb51`. Метка запущенных API/worker: `473f839cae7b790510d149bace9ee953b297f819`, запущены 24 сентября. Метка образа не доказывает тождественность нынешнему рабочему дереву. Замеры относятся к запущенным контейнерам, ссылки на код — к проверенному рабочему дереву.
- Код продукта, конфигурация запуска, службы и данные не изменялись. Нагрузочные тесты и перезапуски рабочего сервера не проводились.

CPU Docker приведён в его шкале: 100% соответствует одному полностью занятому логическому CPU. Его нельзя напрямую сравнивать с общим процентом Windows. Системный снимок Windows показывал около 5% общей загрузки CPU. Средние и максимумы — только для короткой серии, не для суток.

Основные контейнеры Patrol360 с вебом и proxy — около 626 МиБ; с Redis/RabbitMQ/MinIO — около 841 МиБ, без тестовых БД.

Windows видит 31,06 ГиБ физической RAM. В серии было доступно 9,8–10,0 ГиБ. Отдельный поздний снимок показывал 10,2 ГиБ доступной RAM. На компьютере также работают настольные приложения: Codex/ChatGPT около 1,87 ГиБ рабочего набора, Yandex Browser около 1,85 ГиБ, процессы Internet Explorer около 0,77 ГиБ, Node около 0,84 ГиБ, Edge около 0,46 ГиБ. Некоторые относятся к текущей рабочей/диагностической сессии.

Эти значения нельзя складывать с vmmem и контейнерами: существуют вложенные и разделяемые учёты памяти. Рабочий набор процесса также не равен гарантированно освобождаемой памяти. В `.wslconfig` `memory=16GB` — предел, не постоянное резервирование; наблюдаемый рабочий набор vmmem около 2,21 ГиБ.

## Наиболее крупный расход: память ядра Windows

Повторные системные снимки показали около 6,50 ГиБ nonpaged pool и 1,75 ГиБ paged pool. Для paged pool размер выделения не равен полностью резидентной RAM. Система работает с 9 сентября, около 18 суток.

Распределение nonpaged pool по крупнейшим тегам:

| Тег | Размер |
| --- | ---: |
| NVRM | 3409,95 МиБ |
| Wait | 780,05 МиБ |
| File | 607,03 МиБ |
| EtwB | 91,96 МиБ |
| smNp | 91,75 МиБ |

На машине загружен NVIDIA `nvlddmkm.sys` версии 32.0.15.8157 / 581.57; его бинарный файл содержит `NVRM`. Это основание проверять тракт NVIDIA/WSL/GPU первым. Однако наличие строки в драйвере не доказывает, какой процесс инициировал выделение, что весь объём является утечкой или сколько памяти освободит обновление драйвера. Однократно GPU показывал 25% загрузки и 6831 МиБ занятой видеопамяти из 16311 МиБ; видеопамять не прибавляется к RAM Windows. По процессам `nvidia-smi` не дал пригодной для распределения памяти информации (`N/A`).

Следующий обоснованный диагностический шаг — сравнить теги при одинаковой нагрузке во времени и в согласованном окне после закрытия GPU-клиентов по одному. После установления источника проверять конкретное изменение драйвера/клиента. Пока не предлагается перезагрузка как «исправление» или обновление драйверов вслепую. Microsoft рекомендует исследовать рост байтов по тегу для диагностики утечки: [PoolMon: обнаружение утечки](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/example-9---detecting-a-pool-memory-leak).

Это приоритетная диагностика для многогигабайтной проблемы, а не уже доказанная оптимизация приложения.

## Оптимизации с подтверждённым механизмом эффекта

### 1. Убрать неиспользуемую инфраструктуру из постоянного запуска

В проверенных C#-исходниках и зависимостях проекта не найдены клиенты Redis, RabbitMQ или MinIO. Используются `AddMemoryCache` и `LocalAttachmentStore`: [регистрация хранилища](../libs/infrastructure/DependencyInjection.cs). Все три сервиса, однако, запускаются без специального профиля: [compose](../infra/docker/compose.yaml).

Дополнительные факты с работающего сервера:

- Redis: около 130 тысяч команд, статистика команд содержит только PING и наш INFO; попаданий/промахов кеша нет.
- RabbitMQ: нет подключений, очередей и потребителей на момент проверки.
- MinIO: каталог `/data` около 136 КиБ, только служебная `.minio.sys`, пользовательских бакетов не обнаружено.

Предложение: вынести эти сервисы в явный необязательный профиль и исключить из штатного запуска после контрольной проверки внешних зависимостей. Сохранить их тома и возможность обратного запуска. Ожидаемый эффект по текущему замеру — убрать около 215 МиБ контейнерной памяти и их постоянные проверки. Освобождение Windows RAM может отразиться с задержкой из-за WSL/кеширования; это не обещание точного изменения графика диспетчера задач.

Тестовые `patrol360-ppe-test-20260913` и `atom-summary-fix-test-20260923` не имели клиентских подключений. Их запускать только на время соответствующих тестов, с гарантированной очисткой работающего экземпляра после теста. Дополнительно около 71 МиБ по текущему замеру. Сами базы/тома для этого удалять не требуется.

### 2. Один раз читать шаблоны смены в цикле ЭМУ

`RefreshNotifications` перебирает события выхода и рабочие интервалы. Внутри циклов вызывает `BuildDefaultShift`, который через `ResolveShiftTemplate` выполняет `FirstOrDefault` по таблице шаблонов. Получается повторение небольшого SQL для каждой записи, хотя шаблоны внутри одного прохода одинаковы.

- [Цикл событий, строка 158](../libs/infrastructure/Persistence/Emu/EfEmuService.Maintenance.Notifications.cs#L158).
- [Второй цикл, строка 289](../libs/infrastructure/Persistence/Emu/EfEmuService.Maintenance.Notifications.cs#L289).
- [SQL разрешения шаблона, строка 21](../libs/infrastructure/Persistence/Emu/EfEmuService.Helpers.Shifts.cs#L21).

За 436 секунд `emu_shift_templates.seq_scan` вырос на 357 — около 49 чтений в минуту. Статистика таблицы сама по себе не устанавливает вызывающий метод, но найденная цепочка прямо показывает повторные запросы. Worker запускает ЭМУ каждую минуту.

Предложение: загрузить небольшой набор шаблонов один раз в начале прохода, передать его в расчёт, использовать словарь по типу смены. Не вводить длительный глобальный кеш: новый проход увидит изменения настроек. Сохранить семантику fallback и разрешения кодов.

Доказуемый эффект — вместо N чтений справочника одно чтение в проходе; меньше сетевых обращений к PostgreSQL и выделений EF. Процент ускорения всего сервера до реализации не установлен.

Проверенный эквивалентный SELECT занимает 0,051 мс внутри PostgreSQL, читает одну страницу из кеша, в таблице две подходящие для проверки строки. Новый индекс здесь не нужен. Это оптимизация повторения запросов, а не медленного поиска.

### 3. Прекращать обновления скрытых вкладок веб-панели

В [assignmentAutoRefresh.ts](../apps/web/src/features/patrol/assignments/assignmentAutoRefresh.ts) таймер вызывает обновление каждые 10 секунд без проверки `document.visibilityState`. Обработчик `visibilitychange` уже существует, но защищает только событие, не таймер. В [AssignmentScreen.tsx:357](../apps/web/src/features/patrol/AssignmentScreen.tsx#L357) каждый цикл запускает три группы загрузок: назначения, данные обходов и обращения.

В [useSystemNotifications.ts](../apps/web/src/hooks/useSystemNotifications.ts) аналогично действует минутный таймер без проверки видимости.

Предложение: пропускать периодический опрос скрытой вкладки, объединять одновременные вызовы, при возврате выполнять одно актуальное обновление. Доставку уведомлений и требования фонового оповещения согласовать отдельно: при необходимости оставить только лёгкий канал оповещения, не полную загрузку экранов.

Доказуемый эффект — исключение ненужных циклов и их HTTP/SQL при скрытой вкладке. Таймер назначений настроен на максимум около 6 циклов/минуту; фактическая частота скрытой вкладки зависит от throttling браузера. Не заявляется точное число HTTP на цикл без сетевого прогона. При закрытых/неактивных экранах, как в измеренный час, существенного текущего выигрыша не будет. На странице PERCo проверка видимости уже реализована — повторно добавлять её не нужно.

### 4. Уменьшить дублирование тяжёлого readiness

API и proxy обращаются к `/health/ready` каждые 10 секунд. [ApplicationReadinessProbe.cs](../apps/api/Services/ApplicationReadinessProbe.cs) при каждом вызове открывает подключение PostgreSQL, проверяет неприменённые миграции через EF и создаёт/удаляет тестовый файл. За 436 секунд таблица истории миграций получила ещё 85 сканирований — согласуется примерно с двумя проверками каждые 10 секунд. За час через proxy прошло 359 проверок, прямые API-проверки сюда не входят.

Предложение: объединять одновременно выполняемые проверки, тяжёлые проверки схемы выполнять на запуске/после миграции, проверку зависимостей ограничить согласованным интервалом, например 30 секунд. Proxy должен проверять также собственную способность обслуживать запрос, но не дублировать без необходимости полный аудит схемы.

При изменении обоих интервалов с 10 до 30 секунд их плановая частота уменьшается примерно с 12 до 4 вызовов в минуту, то есть на 2/3. Это сокращение запросов и файловых операций, не обещание уменьшения общего CPU на 2/3. Контроль доступности БД/хранилища и readiness при запуске сохранить; задержку обнаружения отказа проверить отдельно.

### 5. Реже записывать успешный heartbeat worker

В [Worker.cs](../apps/worker/Worker.cs) push-цикл работает каждые 5 секунд. Даже пустой успешный цикл вызывает `WorkerDiagnostics.Update`, сериализует состояние, пишет временный файл и заменяет heartbeat. Это до 17 280 записей в сутки только от push, без учёта длительности операций и других циклов.

Предложение: состояние успеха обновлять в памяти, успешный heartbeat записывать раз в 30 секунд; ошибки фиксировать сразу. Сохранить диагностику отдельных направлений и защиту healthcheck от реально зависшего worker. Это доказуемо уменьшает файловые операции; выигрыш CPU/RAM сейчас небольшой — worker и так потребляет в среднем 0,06% одного ядра. Выполнять после более полезных пунктов.

## Что не требует преждевременной переделки

- Потоковая загрузка мобильных файлов уже используется: буфер 81 920 байт и IncrementalHash в [EfMobileAppService.Files.cs:195](../libs/infrastructure/Persistence/MobileApp/EfMobileAppService.Files.cs#L195). Перевод этого пути на «стриминг» повторно не даст эффекта.
- В текущем коде ключи страницы работ ограничиваются `pageSize + 1` до материализации; подробности читаются для итоговых ID: [WorkItemsPaging.cs:58](../libs/infrastructure/Persistence/MobileApp/EfMobileAppService.WorkItemsPaging.cs#L58).
- Кеш файлов печати уже ограничен 64 МиБ, параллельные преобразования — четырьмя. В измерении Gotenberg не работал. Уменьшать эти параметры ради текущего RAM без нагрузочного теста нет основания.
- PERCo использует очередь затронутых сотрудников. По журналу за сутки: 288 успешных синхронизаций событий, среднее 0,333 с, максимум 0,785 с; 24 синхронизации сотрудников, среднее 0,153 с, максимум 0,200 с. Очередь пересчёта пустая. Это wall-clock длительность, не время CPU. Синхронизацию каждые 5 минут замедлять ради гипотетической экономии не предлагается.
- Внутри пересчёта присутствия читается вся история затронутых сотрудников. Это будущая точка роста затрат; текущие показатели не обосновывают рискованное изменение правил расчёта. Сначала нужен прогон большого объёма на копии БД.
- PostgreSQL: между двумя снимками только 5 новых чтений блоков, temp_bytes и temp_files не выросли, deadlocks не изменились и равны нулю. В обоих снимках пять idle подключений и наш SELECT. Не найдено оснований расширять shared_buffers или резко сокращать пулы соединений.
- 15,9 ГиБ временных файлов PostgreSQL — накопленный счётчик за неизвестный период, не текущая память и не обязательно проблема нынешней версии. Большие исторические seq_scan аналогично не доказывают горячий запрос сегодня.
- `pg_stat_statements` не включён; точного рейтинга SQL по общему времени нет. Для дальнейшей оптимизации включить его в отдельном согласованном окне, затем собрать рабочий пик. Во время этого аудита конфигурация БД не менялась.
- Жёсткое урезание RAM Docker/.NET, принудительный GC, очистка кешей по таймеру и увеличение swap не являются доказанным устранением причины. Особенно нельзя интерпретировать лимит WSL 16 ГиБ как его текущее потребление.

## Порядок дальнейшей работы и проверка эффекта

1. Для большой проблемы RAM — установить владельца/динамику NVRM и остальных крупных тегов, отделить GPU/настольную нагрузку от серверных служб. Без остановки рабочих функций в случайный момент.
2. Для небольшой, но подтверждённой экономии — исключить лишнюю инфраструктуру и забытые тестовые БД из постоянного запуска; после этого повторить контейнерные и системные замеры.
3. Устранить повторные чтения шаблонов смен ЭМУ. Тест фактического `RefreshNotifications`: число SQL по шаблонам не растёт с числом событий/сотрудников, результаты решений совпадают.
4. Исправить опрос скрытых вкладок и повторное readiness. Проверить счётчики HTTP/SQL на одинаковом числе вкладок, при скрытии/возврате, недоступности БД и запуске после миграции.
5. При необходимости сократить heartbeat-записи. Проверить зависание отдельного направления и сохранение диагностики ошибок.

Приёмка изменений: одинаковые данные, одинаковое число клиентов, отдельный сценарий загрузки фото, активного ЭМУ и синхронизации PERCo; до/после — RAM, CPU, SQL-вызовы, HTTP, p95 времени ответа. Изменения этого аудита ещё не внедрены, сравнительных результатов после оптимизации нет.
