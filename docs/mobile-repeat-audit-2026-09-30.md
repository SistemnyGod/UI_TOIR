## Локальная сеть и TLS

Проверенный основной адрес: **`https://192.168.2.194`**, порт **443**. `/api/v1/mobile/health` вернул HTTP 200, `status: ok`, `syncProtocolVersion: 1.0`, `contourId: patrol360-local-enterprise`. TLS 1.3 прошёл проверку цепочки с публичным Root CA приложения и проверку имени; SAN содержит `192.168.2.194`. Сертификат действует до 23 августа 2028. Проверка выполнялась без отключения TLS-проверок: [результат HTTPS](<C:/Users/AI_server/Desktop/Proekt obhod/output/mobile-repeat-audit/https-lan-health.json>).

Windows без установленного локального Root CA отклоняет этот сертификат. Это отличается от модели APK: в сгенерированном Android `network_security_config.xml` для `192.168.2.194` присутствуют `@raw/patrol360_local_root_ca` и системные CA. Публичный сертификат действительно включён в сгенерированные ресурсы. Нативная проверка TLS новым установленным APK пока не выполнена.

Из отдельно запущенного Android API 36.1 эмулятора получен настоящий JSON health по поддерживаемому старому HTTP-порту 5173: [Android LAN-проба](<C:/Users/AI_server/Desktop/Proekt obhod/output/mobile-repeat-audit/android-lan-health.log>). Проба использовала точный HTTP-запрос и открытый до ответа сокет. Это проверка доступности API из Android; она не доказывает доступность из отдельного телефона по Wi-Fi. Эмулятор работал с новым образом данных, после проверки остановлен.

Сохранённый старый локальный HTTP-адрес поддерживается. Операция, начатая по HTTPS, не переходит на HTTP при ошибке сертификата. Тесты проверяют нормализацию старых портов/API-путей, запрет URL с credentials, исключение незаданного резерва, сохранение явно выбранного LAN-адреса и отказ от сохранения чужого контура.

## Что остаётся непроверенным и требует следующего прогона

Полная standalone Debug APK-сборка остановилась сначала на разрешении Kotlin из недоступного Maven. Офлайн повтор с теми же версиями плагинов из локального кеша прошёл дальше, но остановился на отсутствующем `com.facebook.device.yearclass:yearclass:2.1.0`: [обычная сборка](<C:/Users/AI_server/Desktop/Proekt obhod/output/mobile-repeat-audit/android-build.log>), [офлайн сборка](<C:/Users/AI_server/Desktop/Proekt obhod/output/mobile-repeat-audit/android-build-offline-retry.log>). Версии зависимостей и модуль `expo-device` не заменялись для обхода ошибки. Новый release APK не выпускался.

После восстановления доступа к Maven нужна сборка и прогон на Android/целевом телефоне: SQLCipher/SecureStore, миграция существующей базы, остановка процесса во время записи/отправки, новая сеть после потери ответа, camera/gallery/NFC/QR, смена пользователя и восстановление токенов. Успешная доставка настоящего отчёта с вложениями в авторизованной серверной сессии в этом проходе не проверена.

Нужно отдельно измерить время и память на больших очередях/галерее: подготовка медиа всё ещё обходит управляемый каталог для оценки квоты (параллелизм ограничен четырьмя). Проверка содержимого миграции выполняет сортировку на стороне SQLite и требует места для её временных страниц. ОС может оставить нативную загрузку работающей после timeout, если отмена зависла; очередь освобождается, а повтор использует исходный clientFileId и серверную идемпотентность. Эти ограничения отражены явно, без утверждения о полном нагрузочном или нативном QA.
