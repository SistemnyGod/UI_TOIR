# Повторные уведомления мобильного обхода — 08.10.2026

## Статус

Исправления внесены в исходный код и проверены. Рабочая БД и контейнеры не изменялись;
новый APK не собран и не установлен. ADB не обнаружил подключённых устройств.
Связь каждого из трёх уведомлений на конкретном телефоне с FCM messageId пока не проверена.

## Подтверждённые источники повторов

1. Worker повторял весь список устройств при отказе хотя бы одного токена.
   Лимит — три попытки. Успешный телефон мог получить один и тот же notificationId
   трижды из-за другого недействующего/временно недоступного токена.
2. Прямой FCM data payload содержал `title`. Установленная версия Expo сама
   показывает такие сообщения на Android, а фоновая JS-задача дополнительно
   вызывала `scheduleNotificationAsync`. Эта задача вызывается и в foreground.
   Поэтому получались два независимых пути показа одного события.
3. Foreground-обработчик разрешал звук и показ при каждой доставке без проверки
   бизнес-ID; стабильного Android `tag` в серверном payload не было.

Проверка рабочей БД выполнена в транзакциях READ ONLY, без вывода токенов и персональных данных:

| Статус push | Попытки | Записей |
| --- | --- | --- |
| failed | 3 | 30 |
| sent | 1 | 110 |
| sent | 2 | 4 |
| sent | 3 | 1 |

Среди ошибок есть `NotRegistered`, `Requested entity was not found` и ошибки
доступа к OAuth-сервису. Дублей по `(mobile_account_id, idempotency_key)` нет.
Одинаковых событий с одинаковым содержимым и объектом в пределах одной минуты
под разными ID также не обнаружено. Это указывает на транспорт/показ, а не
дублирование строк локального журнала.

Источник поведения Expo: [тип уведомлений и исключение Android data title/message](https://docs.expo.dev/push-notifications/what-you-need-to-know/#headless-background-notifications).
Проверены и локальные `FirebaseMessagingDelegate`, `ExpoHandlingDelegate`,
`RemoteNotificationContent`, `RemoteMessageSerializer` установленного expo-notifications 56.
Недействительный токен определяется только по
[FCM Unregistered](https://firebase.google.com/docs/cloud-messaging/error-codes);
InvalidArgument не отзывает регистрацию, поскольку может означать ошибку payload.

## Что изменено

- `EfMobilePushDeliveryService` сохраняет SHA-256 токена каждого успешного
  обращения к провайдеру. При повторе и перезапуске уже подтверждённые токены
  пропускаются. Ошибка одного устройства не прекращает отправку другим.
- `FirebaseMobilePushSender` переводит Unregistered в отдельную ошибку;
  worker отзывает только недействительную push-регистрацию, сохраняя сессию входа.
  При отсутствии пригодных устройств запись остаётся доступной через синхронизацию.
- Миграция `20261008112000_MobilePushDeviceReceipts` добавляет
  `mobile_notifications.push_delivered_token_hashes` (`text[]`, по умолчанию пустой).
  Существующая история не изменяется. Сырые токены в новом поле не сохраняются.
- Сервер отправляет `tag=notificationId`, текст в `message`, канал `patrol360`.
  `body` сохранён для совместимости старого клиента. Разные события сохраняют разные ID.
- Фоновая задача не создаёт локальную копию сообщения, которое показывает
  Android/Expo или ОС. Открытие уведомления только обновляет данные.
- Для настоящих headless payload остаётся локальный показ: до ожидания сервера,
  с защитой от одновременных вызовов и проверкой уже видимой записи в системной шторке.
  Ошибка показа допускает повтор, ошибка синхронизации не вызывает второй показ.
- В foreground повторный бизнес-ID не создаёт новый звук/баннер/запись.
  Пустые транспортные сообщения не показываются и не блокируют последующий локальный alert.
- Поздний cold-start callback после закрытия подписки не выполняет навигацию.
- JSON в `dataString` разбирается отдельно от сырых title/message FCM: заголовок
  внутри JSON сам по себе не означает, что Android уже показал уведомление.

## Применение

1. Сделать резервную копию рабочей БД. Применить добавочную миграцию перед запуском
   версии worker/API, которая читает новое поле.
2. Выпустить worker с исправлением; обновить APK на Android с исправлением обработчика.
   Эти изменения не требуют очистки данных приложения и не затрагивают неотправленные отчёты.
3. Проверить одну тестовую заявку: открытое приложение, свёрнутое приложение,
   перезапуск и открытие уведомления. Проверить количество записей и звуков на телефоне.
4. Старые failed-уведомления не переотправлять массово: они могли быть получены
   одним устройством ещё до появления подтверждений для каждого токена.

Подтверждение провайдера не равно прочтению пользователем. Если FCM принял запрос,
а worker остановился до записи подтверждения в PostgreSQL, повтор всё ещё возможен.
Стабильный tag заменяет запись в шторке, foreground защита подавляет повторные callback;
абсолютная гарантия exactly-once при потере подтверждения провайдера не заявляется.

Полная эксплуатационная приёмка требует обновлённого APK на телефоне и фактического FCM.
Временные тесты не отправляли сообщения реальным пользователям.
