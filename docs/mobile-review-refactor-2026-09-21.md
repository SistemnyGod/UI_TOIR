# Дополнительное ревью мобильных обходов — 21 сентября 2026

## Итог и границы

Проверены текущие исходники React Native / Expo, репозитории SQLite, HTTP-клиент, история отчётов и серверные операции обходов. Исправлены найденные регрессии. Это не приёмка всего предыдущего плана: разрешение конфликта отмены с офлайн-завершением и полноценная переписка пока не реализованы.

Работа выполнена поверх существующих незакоммиченных изменений. Производственное развёртывание и проверка на физическом телефоне не проводились.

| Приоритет | Проблема и последствие | Исправление |
| --- | --- | --- |
| P1 | Пустой выбор исполнителя превращался в запрос активного обхода всего общего аккаунта | Главная не запрашивает активный обход без определённого сотрудника. Недоступный сохранённый маршрут не заменяется чужим. Удалено неявное сохранение выбора при чтении главной |
| P1 | Экран принятия повторно выбирал сотрудника после принятия и стирал сохранённый текущий маршрут | Удалён повторный сброс контекста; выбор сохраняет репозиторий принятия |
| P1 | Ограничение переключения только по списку кандидатов можно обойти устаревшим переходом | Сравнение сотрудников добавлено внутрь SQLite-транзакции до изменения назначений и очереди |
| P1 | Конкурирующие изменения контекста могли терять выбранного сотрудника | Записи SecureStore сериализованы; аккаунт фиксируется до ожидания очереди |
| P1 | Серверная копия отчёта заменяла признак локальной доступности; раздельные страницы давали дубли | Один SQL-список объединяет записи до ограничения количества. Локальная доступность сохраняется, серверные страницы кешируются транзакцией |
| P1 | Запоздалый ответ после смены аккаунта мог попасть в чужой кеш | Область аккаунта и контура фиксируется при начале загрузки и проверяется перед сохранением/показом |
| P1 | Кнопки разрешения конфликта отмены меняли только статус обращения | Удалены недостоверные решения `acceptReport` / `saveCancellation`. Завершённый сервером обход не отменяется задним числом; поздний запрос отмены становится неактуальным |
| P1 | Новая миграция обращений не имела атрибутов регистрации EF | Добавлены `DbContext` и `Migration`, чтобы она обнаруживалась при обновлении базы |
| P2 | Нестабильный focus callback журнала перезапускал загрузку при отрисовке, старые ответы заменяли новые | Загрузка вынесена в `usePatrolReports`, введены поколение загрузки и объединение событий синхронизации; список остаётся видимым при обновлении |
| P2 | Скрытые экраны продолжали подписываться на синхронизацию | Подписки главной, журнала и списка точек ограничены фокусом. Список точек не инициирует сетевое обновление после каждого изменения локальных данных |
| P2 | Журнал создавал запрос состояния доставки для каждого отчёта | Состояния читаются пачкой, максимум 250 назначений на SQL-запрос; длинный журнал использует FlatList |
| P2 | Кешированные подробности сначала запрашивались по сети | Валидная локальная копия открывается первой; JSON проверяется схемой. Отсутствие офлайн-фотографий обозначено явно |
| P2 | Health-проверка скрывала проблему авторизации, старый ответ перекрывал новый успех | Состояние связи вынесено в ConnectionMonitor; успешный публичный health не снимает необходимость входа; устаревшие результаты игнорируются |
| P2 | Инвалидация health-кеша не мешала старому запросу заполнить его заново | Запись и удаление pending привязаны к конкретному запросу |
| P2 | Ожидание общей кешированной проверки обходило оставшийся бюджет | Ожидание каждого кандидата ограничено остатком общего 12-секундного бюджета проверки серверов |
| P2 | Пагинация истории на сервере применяла Skip до сортировки | Сортировка перед Skip; курсор использует время завершения и ID, учитывает пустую дату; неверный курсор возвращает 400 |

В списке точек дополнительно разделены подписи «обработано», «осмотрено» и «не осмотрено». Локальное сохранение и подтверждённая сервером доставка остаются разными состояниями.

## Что ещё не закрыто

1. **P1: отмена до получения офлайн-отчёта.** Нет полного пути: сохранённый снимок результатов и вложений → идемпотентная отправка материалов конфликта → просмотр диспетчером → реальное решение с проверкой версии и аудитом. Нельзя заменять это изменением подписи обращения. Требуется отдельная серверная сущность конфликта и тест обеих резолюций, включая повторную отправку.
2. **P1: история переписки.** Сотрудник может создавать отдельные сообщения, но ответ диспетчера остаётся одним полем `Reply` и перезаписывается. Нужны неизменяемые записи сообщений с автором, временем, operation ID, доставкой и привязкой к одному обращению; повторный запрос отмены должен открывать эту переписку.
3. **P2: общий срок обычной API-операции.** 12 секунд ограничивают поиск сервера в проверке подключения. Для обычного запроса, повторов по резервным адресам и refresh токена ещё нужен общий deadline; вложения требуют отдельной политики. Не следует считать лимит проверки связи ограничением всей синхронизации.
4. **P2: согласованность локального выбора при переключении.** Назначения и outbox меняются одной SQLite-транзакцией, но выбранный текущий маршрут сохраняется отдельно в SecureStore. При отказе SecureStore переключение уже выполнено; нужен механизм восстановления либо перенос контекста в SQLite. Также автоматический выбор единственного сотрудника на главной пока вычисляется при чтении, а не фиксируется отдельной операцией.
5. **P2: серверная карточка отчёта и визуальная приёмка.** Подробности пока упрощены: нет полноценного просмотра вложений и отдельной информации о ручном осмотре в серверной истории. Нужна сверка всех экранов с утверждёнными макетами на малом экране и увеличенном шрифте.

## Проверки

- Полный мобильный `npm run verify` прошёл: 98 тестов node:test + 75 Vitest = **173 теста**, затем проверка кодировки, TypeScript и линтер.
- Добавлено 11 регрессий: контекст аккаунта, запрет чужого переключения, объединение отчётов, кеш без сети, старый контракт пагинации, порядок результатов и авторизация индикатора связи.
- Серверный ATOM-сценарий прошёл на временной PostgreSQL-базе: принятие, неверный исполнитель, A → B → A, повтор операции, устаревшая версия, решения отмены, запрет фиктивного разрешения, курсорная и старая пагинация с одинаковым временем завершения.
- Все **7 тестов MobileAppDbIntegrationTests** прошли на временных PostgreSQL-базах, без пропусков; проверены также сохранение outbox, изоляция operation ID аккаунтами, жизненный цикл назначения и мобильные сессии.
- API собирается: 0 ошибок, 0 предупреждений. TypeScript веб-приложения проходит.
- Реальный NFC, два физических телефона, миграция старой SQLite на устройстве, фоновые ограничения ОС, батарея, нехватка диска и визуальная приёмка **не проверены**.

## Оптимизация по замерам

В этой итерации устранены подтверждённые причины лишней работы: повторные загрузки журнала, запросы статусов по одному отчёту, подписки скрытых экранов и повторное заполнение сброшенного кеша. Проценты ускорения не измерялись.

Следующий замер следует делать на одном устройстве и одинаковом наборе маршрутов/фото: холодное и повторное открытие экрана, p50/p95 сохранения точки, число HTTP-запросов на один цикл синхронизации, время доставки, пиковая память и расход батареи за смену. Изменять индексы, сжатие медиа и параллельность загрузки стоит после этого сравнения.
