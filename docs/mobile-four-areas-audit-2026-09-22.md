# Аудит четырёх участков мобильного приложения

Дата: 2026-09-22. Прикладной код не изменялся. Диагностика: `node tools/audit-mobile-four-areas.cjs`.

Метод: исполнение текущих TypeScript-функций после транспиляции, SQLite в памяти; сетевые ответы и задержки управляемые. Для истории сохранение самих работ заменено коллекцией: тест проверяет алгоритм обхода страниц и реальное SQLite-состояние курсоров, но не весь репозиторий работ. Это не аппаратная приёмка.

## P1: существующая отметка миграции блокирует создание новой таблицы

`src/db/database.ts:387`: work_item_refresh_state создаётся в 20260922_work_paging_and_drafts. Другого создания этой таблицы не найдено. Фактическая runLocalMigration при существующей отметке не вызывает действие. На модели старой базы без новой таблицы после вызова таблицы по-прежнему нет. Сценарий относится к устройствам, уже выполнившим прежнюю редакцию миграции; наличие таких установок на реальных телефонах не проверялось.

Исправление: отдельная добавочная миграция, идемпотентное создание таблицы и добавление колонок. Проверить старую и чистую базы, повторный запуск и сохранность черновиков/очереди.

## P1: автосохранение может восстановить удалённый черновик

`src/features/emuTask/WorkAccountingScreen.tsx:280,348`; `src/db/repositories/workDraftRepository.ts:45,96`. Таймер отменяется при очистке эффекта после закрытия формы, а форма закрывается после ожидания удаления. Репозиторий фиксирует поколение при вызове сохранения, а не при планировании таймера.

Воспроизведение: удалить строку, задержать завершение вызова удаления, вызвать ранее запланированное автосохранение, завершить удаление. Фактический репозиторий оставляет в SQLite восстановленный текст latest. Это управляемая гонка репозитория, не тест React-планировщика на устройстве.

Исправление: контроллер формы синхронно закрывает приём записей и отменяет таймер, ожидает текущую запись, удаляет запись, затем закрывает форму. Старые callbacks должны иметь идентификатор сессии контроллера. Аналогичный барьер нужен при успешной отправке формы. Ошибка удаления возвращает доступное редактирование и повтор.

Дополнительно: deleteWorkDraftForContext использует contourId контекста для ключа ожидания, но deleteWorkDraftInTransaction удаляет по currentContourId. Сейчас контур обычно фиксирован сборкой, однако контракт функции не обеспечивает удаление по переданному контексту.

## P2: сохранённый курсор обновления не используется

`src/services/workTaskService.ts:63-100`: читается boundary_json, а in_progress_cursor только записывается. Повтор начинает с null. Сохранение работ и курсора — разные транзакционные операции.

Фактический тест: 75 старых + 40 новых, отказ второй страницы, пересоздание модуля и повтор. Запросы: null → page2 → null → page2; сохранённый курсор page2; итог 115 записей. Потеря 15 записей в этом сценарии НЕ воспроизвелась: сохранённая прежняя граница защищает от ранней остановки. Отдельная запись данных/курсора здесь означает возможность повторной обработки, а не доказанную потерю.

Исправление: использовать сохранённый курсор, фиксировать страницу и продолжение одной транзакцией; завершение обновления и его граница также должны быть атомарными. Повреждённый boundary_json сейчас заменяется текущими известными строками — риск преждевременного завершения, требующий отдельного теста.

## P2: готовность не доказывает полноту снимка

`src/db/repositories/bootstrapRepository.ts:805-904`; `app/settings/index.tsx:35-41`. Запись непустого входящего набора точек устанавливает snapshot_ready=1. Ожидаемый состав и необходимые справочники не проверяются. Настройки вычисляют готовность только по флагу и положительной версии, не используя количество точек или справочников в условии.

Фактическая функция на SQLite устанавливает ready=1 для одного входящего пункта без проверки справочников. Это доказывает отсутствие проверки; частичная выдача настоящим сервером не воспроизводилась. Также позднее повреждение/удаление точек не учитывается самим условием в настройках.

Ошибка чтения уже снимает зелёный статус — этот прежний дефект сейчас не подтверждается.

Исправление: сохранять доказательство полного снимка (версия, ожидаемые ID/количество, требуемые справочники) в транзакции загрузки; готовность вычислять проверкой этого доказательства и фактических локальных данных. Старым неподтверждённым снимкам оставлять неизвестную готовность.

## Приоритет и границы приёмки

Миграция → контроллер черновика → атомарное продолжение истории → проверка снимка. Затем регрессионные тесты и полный verify, обновление существующей установки, офлайн-перезапуск на телефоне. В этом аудите полный verify, PostgreSQL, NFC и визуальная приёмка повторно не выполнялись. Результат диагностики не утверждает готовность рабочего выпуска.
