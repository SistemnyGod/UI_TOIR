## 1. Приоритетные дефекты основного сценария

### P1-01. Запрос прежнего аккаунта повторяется с новым токеном

**Подтверждено исполнением функции.** `mobileRequestWithinDeadline` запоминает токен первого запроса, но после `401` перечитывает хранилище. Если токен другой, повторяет прежний запрос с ним. Проверки поколения сессии и владельца перед повтором нет.

Воспроизведение: исходный POST для A → задержанный `401` → хранилище уже содержит токен B → тот же путь и тело отправляются под B. Это не доказательство успешной записи чужих данных на сервере: серверные права могут отказать. Но клиент уже допускает отправку операции в неверном контексте. Проверка владельца после HTTP не предотвращает серверный побочный эффект.

Существенное ограничение: обычная смена аккаунта в authService запрещена при неотправленных локальных изменениях. Это уменьшает достижимость сценария для штатной очереди. Диагностика подтверждает дефект транспортной функции при изменившейся сессии, а не обход этой защиты через текущий интерфейс. Сквозную достижимость для каждого типа POST ещё нужно проверить; для отложенных чтений смена аккаунта без очереди остаётся отдельным случаем.

Источник: [httpClient.ts:85](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/api/httpClient.ts:85>), повтор на строках 98–108; вызывающий цикл очереди — [syncEngine.ts:213](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/sync/syncEngine.ts:213>).

**Исправление:** фиксировать владельца и поколение сессии до первого запроса; проверять их перед каждой отправкой, refresh и повтором. Смена поколения прекращает старую операцию; её результат согласуется по исходному ID в исходном аккаунте. Обновление токена того же аккаунта допустимо только при сохранённом контексте.

**Приёмка:** отложенные 401 для GET, POST очереди и загрузки файла; смена A → B и A → B → A. Ни одного повторного POST с токеном другого поколения.

### P1-02. HTTPS сохраняется нормализатором, но не защищён в полном пути подключения

**Подтверждено функциями нормализации, выбора кандидатов и failover.** Для стандартного локального контура `https://192.168.2.194:5173` не входит в разрешённые адреса. При передаче такого preferred-адреса список кандидатов содержит HTTP. Даже если HTTPS явно добавить в allowlist, HTTP остаётся резервным кандидатом.

Контролируемая ошибка TLS для HTTPS приводит к вызову отправки по HTTP. Это касается обычного API; refresh использует тот же подбор адресов. Проверка конкретного адреса в настройках сама по себе не обеспечивает защиту будущих запросов.

**Исправление:** единая политика допуска узла и схемы; для операции, начатой с HTTPS, исключать все HTTP-кандидаты во всех ветвях, включая refresh. Ошибку TLS показывать без обхода проверки сертификата. Сохранённые HTTP-адреса установленных клиентов оставить совместимыми.

### P1-03. Запоздалое завершение NFC возвращает пользователя в старый обход

**Подтверждено обработчиком с задержкой.** После результата сканирования проверяется `screenActiveRef`, затем выполняется `await stopNfcReaderSession()`, после которого переход выполняется без повторной проверки. Воспроизведение: метка A распознана → началось отключение reader → сотрудник ушёл с экрана → отключение завершилось → `router.replace` открывает точку A.

В QR-обработчике нет аналогичной проверки фокуса и поколения вообще. Проверка QR пока по коду, без камеры.

Источники: [ScanNfcScreen.tsx:112](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/features/patrol/ScanNfcScreen.tsx:112>), [ScanQrScreen.tsx:38](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/features/patrol/ScanQrScreen.tsx:38>).

**Исправление:** идентификатор операции сканирования с аккаунтом, назначением, поколением фокуса; проверка после каждого ожидания и непосредственно перед навигацией. Старое завершение не должно останавливать новый reader или сбрасывать его блокировку.

**Приёмка:** уйти к заявкам, открыть B и сменить аккаунт на каждой стадии сканирования/остановки reader. A не открывается позднее.

### P1-04. Ошибка точки оставляет сотрудника без рабочего пути завершения

**Подтверждены участвующие функции; установка статуса прослежена по обработке квитанций.** Невосстанавливаемый автоматически отказ обычной точки переводит назначение в `syncError`. Этот статус запрещает редактирование, сканирование и завершение. Команды завершения ещё нет — общий расчёт правильно говорит, что отчёта нет, но экран вслед за этим обнуляет всю отображаемую доставку.

Если сведения всех точек заполнены, экран предлагает завершить, а репозиторий отвечает «Действие заблокировано текущим статусом назначения». Если сведения неполны, исправление точки также запрещено. Требовать ручного управления очередью от сотрудника здесь недостаточно.

### P1-05. «Продолжить B» может ждать уже архивированную команду

**Подтверждено фактической транзакционной функцией и SQLite.** Проверка `attempt_count > 0` исключает accepted/duplicate/rejected/conflict, но не исключает `superseded` и другие окончательные локальные статусы. Архивированная старая команда B с одной попыткой останавливает продолжение сообщением об ожидании подтверждения.

Источник: [patrolSwitchRepository.ts:157](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/db/repositories/patrolSwitchRepository.ts:157>).

**Исправление:** отделить неизвестный результат отправки от окончательно архивированных команд. Последние не должны удерживать барьер. Неизвестные согласовать по квитанции; не переписывать отправленный payload. Проверить этот же классификатор во всех проверках зависимостей.

### P2-07. Проверка заполненности перехватывает исправление, вход и настройки

**Подтверждён порядок выполнения обработчика.** `handlePrimaryAction` при `!readiness.ready` сразу открывает точки, раньше ветвей `repair`, `signIn`, `serverSettings`. В диагностике `repair` не вызвал переоткрытие ни разу.

Это не означает, что каждый отказ завершения навсегда блокирует исправление: обычный отказ completion и карантин invalidPayload в ряде ветвей уже переводят назначение в inProgress. Но при ошибке файла, заблокированном назначении или проблеме авторизации действие кнопки не соответствует причине остановки. `markOutboxCommandsRejected` при локальной постоянной ошибке файла меняет команду, не переоткрывая назначение.

## 3. История, обращения и списки

### P2-10. Локальная следующая страница отчётов недоступна без сети

**Подтверждено обработчиком журнала:** кеш содержит 75 строк, лимит 25, remoteHasMore=true. «Загрузить ещё» вызывает HTTP до увеличения видимого локального диапазона. Ошибка сети оставляет 25 строк.

Источник: [usePatrolReports.ts:73](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/features/patrol/usePatrolReports.ts:73>).

Кроме того, продолжение и известные ID хранятся в ref экземпляра hook, а не в SQLite. Перемонтирование/перезапуск снова начинает с 25. Обычный blur/focus при сохранённом экземпляре — другой случай; не следует смешивать их.

**Исправление:** сначала расширять доступный диапазон SQLite, независимо от HTTP; отдельно хранить серверное продолжение и достигнутый видимый диапазон по владельцу/контуру.

### P2-11. Начало истории обращений не обновляется до подтверждённой границы

**Подтверждено SQLite:** 25 старых обращений + 40 новых. `loadPatrolAppeals` получает только первую новую страницу; после этого общее число локальных обращений уже >=25 и цикл останавливается. В кеше 50 из 65, 15 новых не запрошены этим обновлением. Это не утверждение об их удалении: они остаются на сервере и могут прийти при последующих корректных запросах.

Источник: [patrolAppealRepository.ts:36](<C:/Users/AI_server/Desktop/Proekt obhod/mobiel proekt/src/db/repositories/patrolAppealRepository.ts:36>).

**Исправление:** завершать обновление по пересечению ID/версии или концу, а не по общему числу кешированных строк. Для начальной подгрузки маршрута без серверного фильтра считать именно подходящие вновь доступные записи.

### P2-12. Несогласованные курсоры обращений скрывают старые и последние страницы

**Подтверждены три ветви:**

1. Сервер выдаёт обращения от новых изменений к старым; локальная страница идёт по `created_at ASC`. После загрузки более старых серверных строк они оказываются перед уже пройденным локальным курсором. В диагностике 25 добавленных строк дали пустую следующую страницу.
2. Если сервер успешно вернул последнюю страницу и `nextCursor=null`, экран завершает loadMore до чтения её из SQLite.

## 6. Порядок исправления и приёмка

1. **Безопасный контекст операции:** запросы/refresh/failover, запрет HTTPS → HTTP, условное сохранение адреса. Тесты смены аккаунта и настроек на каждой сетевой паузе.
2. **Завершение и восстановление:** проблемы точек отдельно от наличия отчёта; точные действия при отказе; исправляемый отчёт переоткрывается; архивированные операции не удерживают B; payload и вложения проверяются строго.
3. **Навигация и формы:** NFC/QR под одним владельцем операции; контроллер сохраняет последнее состояние и первое направление перехода; ошибка видна во всех фазах, повтор не меняет направление.
4. **Локальная история:** кеш прежде сети, независимые курсоры, применение финальной страницы. Сквозные проверки 75/115 отчётов, более 60 обращений, 200+ работ, обрыва и перезапуска.
5. **UI:** тема обязательных полей, честные состояния ошибок, актуальные настройки, фактическая доступность меню. Не добавлять сотруднику новых технических настроек для обхода этих ошибок.
6. **Проверка выпуска:** мобильный verify, веб-тесты/сборка, .NET и включённые интеграции на изолированной PostgreSQL, копия старой SQLite и старого клиента. Затем два телефона и ограниченный пилот.
