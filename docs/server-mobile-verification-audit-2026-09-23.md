# Аудит сервера и мобильного приложения после последних изменений

Дата: 23 сентября 2026 года. Проверено текущее рабочее дерево, включая ранее изменённые и неотслеживаемые файлы.

## Вывод

Текущий работающий сервер отвечает по HTTP 80/5173 и HTTPS 443. Однако согласованный выпуск сервера и нового APK пока не готов к приёмке. В новой Android-конфигурации обнаружен блокирующий дефект; остаются ошибки восстановления очереди, проверки доставки, авторизации загрузки вложений и страниц обращений. Зелёные автоматические проверки этих сочетаний событий не покрывают.

Продуктовый код, рабочие данные и развёртывание в этом аудите не изменялись. Добавлены только диагностические скрипты и отчёт. Аудит не является доказательством отсутствия других ошибок.

## Подтверждённые дефекты

### 1. P1 — сгенерированная Android-сетевая конфигурация содержит повтор адреса

Место: [app.config.js:123](../mobiel%20proekt/app.config.js#L123), формирование XML на строках 133–147.

Для `local-enterprise` адрес `192.168.2.194` присутствует в `localCleartextDomains` и ещё раз в `localHttpsTrustConfig`. Фактический генератор с контролируемыми файловыми операциями выдаёт два `<domain>` с одним именем. Различие `includeSubdomains=true/false` не устраняет дубликат.

Android использует общий набор уже встреченных доменов и выдаёт ошибку `has already been specified`; это подтверждается [исходным кодом Android XmlConfigSource](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/security/net/config/XmlConfigSource.java). Последствие — некорректная сетевая политика новой корпоративной сборки, возможное исключение при её инициализации и блокировка соединений. На телефоне этот сбой не запускался.

Исправить: один блок домена с системным и локальным CA. В этом совместимом выпуске разрешить HTTP для того же домена в том же блоке. Запрет HTTPS→HTTP остаётся отдельной политикой операции. Проверить именно итоговые ресурсы release APK и запуск Android, а не только синтаксис JavaScript.

### 2. P1 — загрузка фото после 401 может повториться с токеном другого аккаунта

Место: [fileApi.ts:18](../mobiel%20proekt/src/api/fileApi.ts#L18), повтор на строках 28–30.

JSON-запросы получили защиту сессии, но `uploadMobileFile` её не использует. Управляемое воспроизведение: файл аккаунта A → запрос с токеном A → смена аккаунта → запоздалый 401 → refresh текущего B → повтор того же файла с токеном B. Получены две попытки с разными аккаунтами. Функция не сравнивает `file.ownerUserId` с зафиксированным владельцем операции.

Это доказательство неправильного повторного запроса, а не доказательство успешного сохранения файла сервером под чужим аккаунтом: серверные проверки принадлежности могут отказать. Риск — смешение контекста и ошибочная обработка доставки/авторизации.

Исправить: фиксировать владельца, контур, поколение сессии и параметры подключения до первого ожидания; проверять перед отправкой, refresh, повтором и применением результата. При смене аккаунта прекращать старую операцию. Добавить регрессию фактического upload API, а не только JSON-клиента.

### 3. P1 — восстановление «Продолжить B» после 404 не восстанавливает архивированную команду

Место: [patrolContinuationService.ts:27](../mobiel%20proekt/src/services/patrolContinuationService.ts#L27), проверка статуса на строке 38.

SQL возвращает только `client_operation_id AS id`, хотя тип результата объявляет ещё и `status`. Поэтому `command.status === 'superseded'` всегда ложно для настоящего SQL-результата.

На SQLite: отклонённое переключение + ранее отправленная архивированная команда B + отсутствующая квитанция. После согласования команда осталась `superseded`, запланирована обычная синхронизация и показано ожидание. Обычная очередь такую команду не выберет; продолжение может ждать бесконечно.

Исправить: читать нужные поля и транзакционно возвращать именно неизвестную операцию в согласованный механизм повтора, сохраняя ID/payload. Не считать любое архивирование окончательным серверным исходом.

Почему тест зелёный: `patrolContinuation.vitest.test.ts` вручную возвращает `{id, status:'superseded'}`, обходя фактический SQL. Нужен тест с настоящим запросом SQLite.

### 4. P1 — проверка доставки по-прежнему не является строгой

Место: [patrolNavigationService.ts:61](../mobiel%20proekt/src/services/patrolNavigationService.ts#L61), выборка файлов на строках 82–86.

При уже полученном состоянии `delivered` проверка вернула `true` для:

- `{"pointResults":[{}]}`;
- `{"pointResults":[null]}`;
- строки вместо списка `photoClientFileIds`;
- ссылки на подтверждённый файл того же аккаунта/контура, но другого назначения и другой точки.

Payload `null` вызывает исключение при чтении `pointResults`. Невалидный JSON `{bad` теперь корректно возвращает `false` — эту часть исправления подтверждаю.

Следствие: повреждённый локальный отчёт может разрешить автоматический выход без полноценной проверки, либо оставить экран с исключением. Это не позволяет обойти серверную проверку нового отчёта: воспроизведение предполагает уже существующую квитанцию и повреждённые локальные сведения.

Исправить: строгая схема полного payload, включая назначение, точки, статусы и массивы файлов; пакетный запрос должен проверять пары назначения/точки. Корректно подтверждённые файлы с удалённой локальной копией оставить допустимыми. Любое повреждение должно дать явное состояние «Требуется проверка».

### 5. P1 — запоздалый QR-результат продолжает навигацию старого обхода

Место: [ScanQrScreen.tsx:50](../mobiel%20proekt/src/features/patrol/ScanQrScreen.tsx#L50).

После `await scanPointByQr` нет проверки фокуса, назначения или поколения сессии. Обработчик всегда вызывает `router.replace` для захваченного назначения. Выполнение фактического обработчика с задержкой подтверждает переход к `OLD/point/.../fill` после времени, в которое пользователь мог уйти с экрана. Это проверка обработчика с управляемым ответом, не тест смонтированного React-экрана.

Исправить: общий владелец NFC/QR-операции, проверка после каждого ожидания, непосредственно перед переходом и в `finally`. Повторный запуск сканера не должен освобождаться старой операцией.

### 6. P2 — обращения обновляются не до подтверждённой границы и теряются из видимого диапазона

Места: [patrolAppealRepository.ts:45](../mobiel%20proekt/src/db/repositories/patrolAppealRepository.ts#L45), [PatrolAppealScreen.tsx:88](../mobiel%20proekt/src/features/patrol/PatrolAppealScreen.tsx#L88).

Несколько независимых воспроизведений:

1. Было 25 кешированных обращений, появилось 40 новых. Загрузилась только первая страница: в SQLite 50 из 65, ещё 15 не запрошены. Причина — остановка по общему количеству кеша `>=25`. Это относится к обращениям; не следует переносить этот вывод на ранее проверенные 115 работ.
2. Сервер выдаёт старую страницу, локальная выдача сортируется `created_at ASC`. Добавленные старые записи оказываются до локального курсора: добавили 25, следующая локальная страница показывает 0.
3. Когда последняя серверная страница уже сохранена и `nextCursor=null`, экран выходит до чтения SQLite. Последние записи не показываются в этом проходе.
4. Первое открытие офлайн начинает HTTP раньше чтения кеша. Ошибка приводит к нулю локальных чтений и пустому экрану при наличии сохранённых данных.
5. Смена поколения во время подгрузки оставляет `loadingMore=true`: старый `finally` не сбрасывает флаг, а новый владелец загрузки явно не создаётся.

Исправить: отдельно обновление начала до фиксированной границы и подгрузка истории; сначала SQLite; порядок `createdAt DESC, ID ASC`; пересогласование видимого диапазона после серверной страницы; чтение последней страницы до объявления конца; блокировка с собственным ID владельца и синхронным захватом.

### 7. P2 — журнал отчётов не раскрывает уже сохранённую следующую страницу без сети

Место: [usePatrolReports.ts:79](../mobiel%20proekt/src/features/patrol/usePatrolReports.ts#L79).

Если `remoteHasMore=true`, «ещё» сначала запрашивает сервер. При сетевой ошибке видимый лимит не растёт. В управляемом сценарии 75 строк доступны локально, но на экране остаются 25 после одной неудачной HTTP-попытки.

Исправить: сначала раскрыть подходящий сохранённый диапазон; только после его исчерпания идти в сеть. Отдельно сохранять серверное продолжение и лимит/якорь отображения.

### 8. P2 — восстановление повреждённой истории работ повторяет начало после обрыва

Место: [workTaskService.ts:82](../mobiel%20proekt/src/services/workTaskService.ts#L82), сохранение продолжения на строке 106.

При распознавании повреждённой границы код начинает recovery, но после страницы обновляет только режим и курсор, оставляя `boundary_json='broken'`. После перезапуска вновь распознаёт повреждение и сбрасывает сохранённый курсор.

Диагностика SQLite: сохранены `refresh_mode='recovery'`, `in_progress_cursor='25'`, но повтор запросил `[null,'25','50','75','100']`. Все 115 строк в конце сохранены; потеря данных здесь не доказана. Подтверждены лишняя загрузка и невозможность устойчиво продвигаться при повторяющихся обрывах.

Исправить: при первом переходе в recovery сохранить валидное описание режима и пустую границу атомарно со страницей; валидный recovery возобновлять с курсора. Тестировать повреждение → успешная страница → обрыв → новая сессия репозитория.

### 9. P2 — после сохранения точки и ошибки перехода основная кнопка перестаёт действовать

Место: [PointFillScreen.tsx:233](../mobiel%20proekt/src/features/patrol/PointFillScreen.tsx#L233).

Успешная запись закрывает контроллер, затем `continuePatrolFlow` может завершиться ошибкой. В этой ветке `finalizingRef` остаётся true; кнопка визуально снова активна после `setIsSubmitting(false)`, но следующее нажатие немедленно возвращается. Фактический обработчик с задержанными зависимостями: одна запись, одна попытка перехода, второе нажатие не повторяет переход.

Данные точки не теряются, и сотрудник может выйти другим действием. Но основной согласованный путь прерывается. Исправить: отдельное состояние «точка сохранена, переход не выполнен» и действие повторить только переход.

## Дополнительные незавершённые места по коду

Эти пункты нельзя выдавать за полный сквозной тест UI на устройстве:

- **Форма и потеря фокуса.** `PointFillScreen.tsx:165` закрывает контроллер в cleanup фокуса без ожидания `flush`. Контроллер при `update → close → flushUntilSettled` выполняет 0 записей. Обычные replace-переходы защищены `usePreventRemove`, но переход с потерей фокуса без удаления экрана требует отдельного mounted-теста. Проверка последней редакции и навигация всё ещё разделены Promise-ожиданиями; это не заявленная единая атомарная операция.
- **Черновики работ.** `WorkAccountingScreen.tsx:310,323` выбирает владельцем редактирования/завершения сотрудника самой работы, а не выбранного исполнителя устройства. Автосохранение этих форм по-прежнему реализовано отдельными эффектами/таймерами. Требуется проверить ввод во время закрытия, удаление при активной записи и смену исполнителя на смонтированных формах.
- **Настройки.** `app/settings/index.tsx:24` загружает сводку по `[connection]`. Смена назначения и события очереди при неизменном сетевом статусе не обновляют сводку напрямую. Последнее обновление данных и последняя подтверждённая отправка не разделены. Ошибка SQLite снимает зелёную готовность — это поведение сохранено.
- **Меню NFC.** `ScanNfcScreen.tsx:330` всё ещё передаёт `status: 'inProgress'`, без фактической capability-модели. Меню может предлагать действия, которые потом отвергает репозиторий.
- **Тема.** `PointFillScreen.tsx:790` и `ScanQrScreen.tsx:139` используют фиксированный тёмный цвет текста. Часть полей не получает тематического переопределения; требуется проверить контраст в тёмной теме. Скриншоты и визуальная приёмка не выполнялись.
- **Строгий порядок сервера.** `ProcessMarkPatrolPoint` проверяет статус и причину, но не проверяет обязательные материалы пропуска на этом промежуточном шаге; их проверяет финальное завершение. Это не выполнение полного согласованного правила промежуточной приёмки. Специального интеграционного сценария новой capability/пропуска/повторного принятия ранее отклонённой точки в просмотренных тестах не найдено.
- **Стоимость строгого порядка.** `GetConfirmedMobilePointResultIds` загружает JSON всех подтверждённых отметок аккаунта, затем фильтрует назначение в памяти, при каждой проверке точки. SQL должен выбирать только необходимое назначение/снимок. Ускорение и новые индексы без замеров не утверждаю.
- **Контекст подключения.** Перед `setServerBaseUrl` есть проверка поколения, но сам setter асинхронный; refresh публикует восстановление авторизации с текущим поколением после ожидания. Требуются тесты смены адреса/сети во время этих ожиданий. Прежнее заявление о полной защите всех поздних результатов шире текущих доказательств.

## Что исправлено и подтверждено в рамках аудита

- Неправильный HTTPS `:5173` нормализуется к `https://192.168.2.194`.
- Для операции, начатой с HTTPS, фактическая функция выбора адресов вернула только HTTPS-кандидаты.
- Сохранённый `http://192.168.2.194:5173` остаётся HTTP.
- Публичный сертификат из проекта соответствует IP и подписан проектным CA; срок сертификата сервера: 21.05.2026–23.08.2028. Рабочий HTTPS также прошёл проверку с этим CA.
- Caddy направляет HTTP/HTTPS в одинаковый API upstream; health возвращает одинаковый контур. Это не проверка всех защищённых API на работающем сервере.
- Добавочные миграции для `refresh_mode` и новой capability имеются. Полная приёмка обновления реальной старой мобильной базы и восстановления бэкапа не выполнялась; тест helper схемы не заменяет фактический миграционный прогон.
- Невалидный JSON отчёта больше не разрешает доставку. Однако валидный JSON неправильной структуры остаётся проблемой из пункта 4.
- Для JSON-запросов добавлена защита повторного 401; её нельзя автоматически приписывать upload-пути.

8. Добавить PostgreSQL-сценарий строгого маршрута: отметка/неисправность/ручной осмотр/пропуск, обязательные фото, повтор прежнего отказа, отмена и идемпотентность. Текущие 189 инфраструктурных тестов не заменяют этот сценарий.
9. Проверить копии прежних баз, резервное восстановление, старый клиент и артефакты выпуска.
10. Пройти основной путь на двух телефонах: A не закончил → B выбрал → завершил офлайн → файлы и отчёт приняты → список → перезапуск не возвращает A. Проверить NFC, QR, фото, HTTPS, клавиатуру, крупный шрифт, «Назад», память и батарею.

До закрытия P1 рабочий выпуск новой корпоративной сборки рекомендовано отложить. В этом аудите не выполнялись APK-сборка/подпись, установка, пилот, измерения скорости/памяти/батареи и восстановление бэкапа. Достоверный процент готовности из числа прошедших тестов вывести нельзя.
