# Дополнительный аудит мобильных обходов и план исправлений

Дата: 22.09.2026. Проверено текущее рабочее дерево, включая незакоммиченные изменения предыдущего этапа. По результатам аудита исправления внесены в мобильное приложение; серверные контракты не менялись.

## Вывод и способ проверки

Предыдущее сообщение о завершении этапа было слишком широким: часть исправлений работала только при благоприятном порядке событий. Найдены девять групп проблем и исправлены в порядке очереди, сохранности отчётов, истории, обращений и связи.

Диагностика: `node tools/audit-mobile-followup-2026-09-22.mjs`.

Скрипт загружает текущие TypeScript-функции приложения. Операции очереди, перенос ID, чтение обращений и SQL миграции выполняются на SQLite в памяти. Для hook журнала и адаптера связи используются управляемые замены React, NetInfo и HTTP. После исправлений скрипт проверяет корректное поведение: сохранение зависимостей, барьер переключения, идемпотентное продолжение, перенос отчёта, непрерывную историю и актуальность связи. Это проверки функций и порядка асинхронных событий, не визуальная или аппаратная приёмка.

После реализации полный мобильный `npm run verify` прошёл: 100 sync-тестов, 80 Vitest-тестов, проверка кодировки, TypeScript и линтер.

## Подтверждённые проблемы

### F1. P1 — повторная отмена разблокирует B без действия сотрудника

Источник: `mobiel proekt/src/db/repositories/patrolCancellationRepository.ts:71`, `outboxRepository.ts:70`.

Первый вызов обработчика отмены сохраняет переключение с неизвестным результатом как `retryLater`. Но после окончательного отказа переключение получает `conflict`/`rejected`, а следующий вызов обработчика отмены переводит его в `superseded`. Для очереди это успешное завершение зависимости. Результат B становится готовым к отправке без отдельной подтверждённой команды запуска B.

Воспроизведение: switch A → B в `sending` → отмена A → ответ `conflict` → повторная обработка отмены A. Фактическая SQL-выборка очереди возвращает `result` B. Нажатия «Продолжить B» не было.

Исправление: разделить окончательный отказ переключения и разрешение зависимостей B. Отказ остаётся барьером до явной операции продолжения либо отмены B. Повторный Bootstrap не должен закрывать этот барьер. Не приравнивать диагностическое архивирование операции к разрешению отправки результатов.

Приёмка: неизвестная квитанция, 404, отказ, повторный Bootstrap и перезапуск не выпускают результаты B. После подтверждения отдельного запуска они отправляются; A не возобновляется автоматически.

### F2. P1 — «Продолжить B» переписывает уже отправлявшиеся команды

Источник: `mobiel proekt/src/db/repositories/patrolSwitchRepository.ts:147`.

Защита проверяет только `status = 'sending'`. Команда после потери ответа уже находится в `retryLater`, хотя её отправка начиналась. Ей меняются порядок и payload с прежним ID. После первого продолжения исходный switch становится `superseded`; второе нажатие отвергается до поиска созданной операции продолжения.

Воспроизведение: команда результата B с `attempt_count = 1`, статусом `retryLater` и зависимостью от switch после продолжения получает дополнительную зависимость `continue`. Повторный вызов выдаёт «Продолжить можно только после отклонённого переключения маршрута».

Исправление: учитывать факт начала отправки, а не только текущий статус. Для неопределённых попыток сначала получать квитанции; неизменяемые команды не переставлять. Хранить связь исходного switch с continuation и возвращать её до проверки статуса исходной операции. В транзакции переставлять только гарантированно не отправленные команды.

Приёмка: потеря ответа на результаты B, перезапуск, двойное нажатие и продолжение с уже созданным запуском. Один ID продолжения, прежние payload отправленных команд неизменны, очередь не имеет циклов.

### F3. P1 — общий механизм постановки в очередь стирает прежние зависимости

Источник: `mobiel proekt/src/db/repositories/outboxSql.ts:21`.

При добавлении барьера переключения `dependencies` заменяются целиком. Воспроизведение: заданная зависимость `photo` исчезает, остаётся только `switch`. Имя `photo` в диагностике обозначает произвольную обязательную предшествующую операцию; это не проверка механизма загрузки файлов.

Исправление: объединение и дедупликация зависимостей в одном общем помощнике для постановки, переключения и восстановления очереди. Исключение самозависимости, проверка циклов. Разрешение зависимости должно учитывать её назначение и итог, а не только общее терминальное состояние.

Приёмка: исходная зависимость и зависимости обеих сторон switch сохраняются; готовность наступает только после выполнения всех необходимых предшественников.

### F4. P1 — при объединении ID отчёт снова исчезает из журнала

Источник: `mobiel proekt/src/db/repositories/outboxRepository.ts:1211`, `bootstrapRepository.ts:62`.

Оба механизма переноса ID остаются раздельными. В объединение назначений не включён `local_report_present`. Когда уже существуют локальная и серверная записи, исходная запись удаляется, а у серверной остаётся флаг 0.

Воспроизведение реального remap: локальная запись `completedLocal`, флаг 1 и дата завершения объединена с серверной `accepted`, флаг 0. После переноса остаётся запись `completedLocal` с датой, но флагом 0. Журнал по новому правилу её не выбирает. Результаты физически не удаляются — теряется видимость отчёта.

Исправление: один транзакционный механизм для Bootstrap и квитанции. Явные правила объединения флага отчёта, исполнителя, ревизий, снимка маршрута и дат; перенос всех ссылок, включая курсоры обращений нового формата. Удалять старый ID только после переноса и проверки ссылок.

Приёмка: два входа переноса ID × наличие/отсутствие серверной записи × отчёт с датой/без даты. Сохраняются отчёт, результаты, файлы, обе стороны switch, обращения, кеши, контекст устройства; другой аккаунт/контур не изменяется.

### F5. P2 — миграция может выдать ошибочный черновик за завершённый отчёт

Источник: `mobiel proekt/src/db/database.ts:410`.

Статусы `syncError`, `authRequired`, `needsDispatcherDecision` используются не только после завершения. Миграция устанавливает флаг отчёта по одному такому статусу. Воспроизведение: у `syncError` без даты и команды завершения `local_report_present` становится 1.

Исправление: восстанавливать наличие отчёта по доказательству завершения: явному локальному завершению, сохранённой дате или действующей команде завершения. Не выводить завершение из ошибки синхронизации. Для уже применённой миграции нужна следующая добавочная миграция; неоднозначные записи сохранять для проверки, не удалять.

Приёмка: ошибка запуска/паузы не создаёт отчёт. Настоящий завершённый отчёт без даты остаётся доступным. Явное переоткрытие не отменяется последующим восстановлением старой команды.

### F6. P2 — журнал зависает после ухода во время запроса

Источник: `mobiel proekt/src/features/patrol/usePatrolReports.ts:55`, `:99`, `:104`.

При уходе поколение запроса инвалидируется; `finally` очищает loading только для действующего поколения. После возврата loading остаётся true, новые загрузки сразу выходят. Также `publishLocal` и `refreshHead` меняют данные без полной проверки поколения внутри своих асинхронных шагов.

Воспроизведение: открыть журнал → задержать HTTP → уйти → завершить HTTP → вернуться. `busy = true`, число новых запросов после возврата и ручного обновления — 0.

Исправление: отдельное владение активным запросом, очистка блокировки по идентификатору владельца, проверка поколения/аккаунта перед каждым изменением состояния. Начатую работу скрытого экрана отменять либо безопасно завершать только в кеше; новую видимую загрузку она не блокирует.

Приёмка: уход на каждой стадии запроса, возврат до/после ответа, смена аккаунта и повторное открытие. Устаревший ответ не публикуется, кнопки снова доступны.

### F7. P2 — обрыв обновления истории оставляет пропуск

Источник: `mobiel proekt/src/features/patrol/usePatrolReports.ts:33`.

Успешно полученная часть незавершённого обновления сразу добавляется в `knownRemoteIds`. После ошибки следующей страницы новое обновление считает первую полученную страницу пересечением с прежней историей и останавливается слишком рано.

Воспроизведение: 75 старых отчётов → 40 новых → первая страница 25 загружена → ошибка второй страницы → повтор обновления. По-прежнему отсутствуют 15 новых отчётов.

Исправление: разделить последнюю полностью подтверждённую границу истории, курсор незавершённого обновления, курсор старой истории и видимый лимит. Частичная страница не становится новой подтверждённой границей. Сохранять состояние продолжения, объединять данные по ID. Признак конца истории не сбрасывать в true просто из-за существования старого курсора.

Приёмка: 75 + 40, обрыв каждой страницы, повтор, выход/возврат, новые записи во время загрузки, окончание истории. Все ID доступны без пропусков и дублей.

### F8. P2 — обращения по-прежнему ограничены первой страницей в интерфейсе

Источник: `mobiel proekt/src/db/repositories/patrolAppealRepository.ts:16`, `:84`; `features/patrol/PatrolAppealScreen.tsx:21`, `:50`.

`loadMorePatrolAppeals` существует, но экран её не вызывает и не показывает подгрузку. На новом сервере маршрут с 60 обращениями показывает 25. На старом сервере поиск останавливается при первой найденной записи нужного маршрута, поэтому полнота его истории также не обеспечена.

Чтение локальных данных одновременно запускает HTTP. Событие синхронизации опять вызывает этот метод; проверено: повторное чтение создаёт второй запрос. Список строится через `items.map` внутри ScrollView — виртуализация не реализована. Ошибки загрузки подавляются и визуально не отличимы от отсутствия новых данных. Нет собственного события репозитория с ID изменённых назначений.

Исправление: разделить локальное чтение, обновление начала и подгрузку старой истории; завершить алгоритм пересечения по ID/версии. Подключить `ScreenList`/FlatList и подгрузку по 25, хранить ошибку и признак неполной истории. Репозиторий объединяет сетевые запросы и публикует адресное событие; экран по событию читает только SQLite. На старом API явно учитывать неполноту общего кеша. Проверять аккаунт после HTTP до записи ответа.

Приёмка: 60+ обращений одного маршрута, старый маршрут за первой страницей, закрытые записи, 40 обновлённых обращений, отключение сети, два параллельных открытия. Событие обновления не создаёт новый HTTP-запрос; скрытый экран не запускает загрузку.

### F9. P2 — контекст авторизации и индикатор связи расходятся

Источник: `mobiel proekt/src/core/connectionStateEvents.ts:15`, `connectionStatus.ts:34`, `connectionMonitor.ts:56`, `api/httpClient.ts:51`.

`beginAuthTransition` увеличивает общее поколение, но не уведомляет монитор об изменении. Монитор продолжает фильтровать по старому поколению, поэтому новый результат восстановления сессии игнорируется. При изменении настроек `reset` очищает authRequired, и публичная health-проверка может вернуть «На связи» без успешного входа.

Оба случая воспроизведены через реальные функции сервиса событий, монитора и адаптера подписки. Кроме того, жизненный цикл монитора всё ещё зависит от подписчиков React, а любое событие NetInfo инвалидирует контекст, даже если существенное состояние сети не изменилось.

Исправление: общий сервис с единым снимком сети, адреса, аккаунта и сессии. Изменение поколения само уведомляет подписчиков. Успешный login/refresh подтверждает именно запущенное поколение; обычный API и health не снимают необходимость входа. Настройки и размонтирование экрана не уничтожают состояние авторизации. Повторные одинаковые события сети не запускают дополнительные проверки.

Приёмка: повторный вход при открытом экране, смена адреса и аккаунта, late response, health после 401, одинаковые NetInfo-события и фон/возврат.

## План реализации

1. **Регрессионная база и метрики.** Превратить диагностические сценарии в тесты фактических функций с SQLite, управляемыми ответами API и жизненным циклом фокуса. Измерить число запросов, SQL-чтений, открытие списка, сохранение точки и синхронизацию на фиксированных данных. Не оценивать производительность телефона по миллисекундам настольной SQLite.
2. **Очередь — F1–F3.** Единый механизм зависимостей двух назначений; явно различать неизвестный результат, подтверждённый отказ и разрешение продолжения. Идемпотентная continuation, неизменяемость отправленных команд, проверка графа зависимостей. Все перестановки в одной транзакции.
3. **Отчёты и ID — F4–F5.** Единый remap из Bootstrap и квитанций; перенос local_report_present; добавочное восстановление исторических ошибок без удаления результатов. Проверки изоляции аккаунта и контура.
4. **Загрузка данных — F6–F8.** Управляемое владение запросами, раздельные курсоры полного/частичного обновления и старой истории. Виртуализированный экран обращений с работающей подгрузкой; локальное чтение по адресным событиям, без повторной сети.
5. **Связь и доступность действий — F9.** Сервис контекста вне React. Общая модель меню должна учитывать реальный статус, неопределённость очереди и возможности сервера: сейчас общий builder унифицирует подписи, но не получает статуса/возможностей и не определяет доступность. Проверить защиту от повторного нажатия паузы и отсутствие лишних действий в закрытом обходе.
6. **Приёмка.** Полный мобильный verify, включённые интеграционные проверки на изолированной PostgreSQL, API и веб-совместимость. Затем два телефона одного аккаунта, NFC, фото, офлайн-перезапуск, крупный шрифт и системная кнопка «Назад». Сравнить метрики на том же наборе данных; память и батарею измерить на устройстве.

Первый результат этапа: ни повторная отмена, ни смена ID не скрывают отчёт и не разрешают преждевременную отправку B. Выпускать сервер → приложение → ограниченный пилот после приёмки.

## Результат реализации

В мобильном коде добавлены барьер переключения до явного продолжения, идемпотентная команда `Продолжить B`, объединение зависимостей с защитой циклов, перенос признаков локального отчёта, добавочная отметка проверки неоднозначных завершений, безопасное владение запросами журнала, продолжение head-обновления после обрыва, локальное чтение обращений по событиям и единый контекст поколений соединения. Общие действия маршрута теперь фильтруются по статусу и возможностям сервера.

Диагностические воспроизведения после исправлений проходят. Полевая проверка NFC, визуальная приёмка и замеры батареи/памяти требуют реального телефона.

## Что оптимизировать по подтверждённым причинам

- Убрать сетевой запрос из чтения SQLite обращений; исключить повторный HTTP в обработчике события синхронизации.
- Догружать список обращений по мере просмотра и виртуализировать рендеринг.
- После обрыва продолжать незавершённую страницу, не начинать всю историю заново и не прекращать обновление на собственной частично загруженной странице.
- Свести зависимости очереди, remap и владение загрузками к общим проверяемым функциям. Это уменьшает число расходящихся веток обработки ошибок.
- Новые индексы, сжатие фото и параллельность отправок выбирать после EXPLAIN/замеров. Отдельный индекс для обращений уже добавлен; доказательств, что именно SQL-индекс сейчас ограничивает работу, в этом аудите нет.

## Ограничения проверки и отдельные задачи

Серверные интеграционные тесты включаются через `PATROL360_RUN_DB_INTEGRATION=true`. После исправлений выполнен выделенный прогон `MobileAppDbIntegrationTests`: 7 тестов прошли на тестовой PostgreSQL. Рабочую БД для приёмочных тестов не использовать.

В этом аудите не выполнялись аппаратные, визуальные и батарейные измерения. Не проводилось рабочее развёртывание.

Полное разрешение конфликта отмены с офлайн-отчётом, история сообщений, просмотр вложений серверных отчётов и общий deadline API остаются ранее выделенными отдельными задачами. Перечисленные F1–F9 находятся внутри последнего утверждённого этапа и не должны подменяться этими будущими функциями.
