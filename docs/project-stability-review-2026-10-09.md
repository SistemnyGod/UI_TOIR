## Подтверждённые замечания

### 1. P1 — старый путь СИЗ позволяет выдачу сверх нормы

Места: `apps/api/Controllers/InventoryController.cs:444–448`, `apps/api/Authorization/PpeIssuanceEnabledAttribute.cs:39–60`, `libs/infrastructure/Persistence/Inventory/EfInventoryWorkflowService.Issue.cs:168–222`, `libs/infrastructure/Persistence/Inventory/EfInventoryWorkflowService.Validation.cs:15–37`.

После включения выдачи и готовности всех наборов старый POST `ppe/cards/{id}/lines` проверяет применимость нормы и утверждение соответствия товара. Но количество и уже выданный объём фильтр не проверяет. `AddPpeCardLine` принимает любое положительное количество и статус `issued`, записывает строку и событие выдачи. Проверка доступного количества, существующая в `CreatePpeIssue`, на этом пути не выполняется. Аналогично здесь нет проверки обязательного размера.

Воспроизведение: фиктивные 34 готовых набора, применимая норма, утверждённый товар, количество по норме 1, уже выдано 1. Запрос с `Quantity=999`, `Status=issued`, пустым размером прошёл фильтр. Контрольный запуск не обращался к БД; последующая возможность записи установлена по обработчику и его валидатору. При выключенной выдаче этот POST блокируется — существующие тесты блокировки прошли.

Исправление: свести все пути создания и изменения фактов выдачи к единой проверке правил, доступного количества и параметров товара. Закрепить проверки бизнес-операцией, а не только MVC-фильтром. Сохранить доступность возвратов и чтения при выключенной выдаче.

### 2. P2 — поздний ответ ручного обновления заменяет результаты другого фильтра

Место: `apps/web/src/hooks/useResultsWorkspace.ts:71–88`; вызов без `AbortSignal`: `apps/web/src/features/patrol/results/ResultsWorkspace.tsx:605`.

`refreshResults` отбрасывает только ответ отменённого запроса с переданным сигналом. Ручное обновление и обновление после архивирования/удаления запускаются без сигнала и без проверки поколения запроса или актуального фильтра.

Воспроизведение: начато ручное обновление старого фильтра → выбран новый маршрут → получен и показан ответ нового фильтра → завершился старый ручной запрос. В таблице появились записи старого маршрута при выбранном новом фильтре. Такой же поздний отказ может очистить новую выборку через ветку обработки ошибки.

Исправление: общий идентификатор владельца/фильтра и поколение загрузки для всех обновлений, включая ручные; проверка актуальности перед любым изменением данных и ошибки.

### 3. P2 — дозагрузка смешивает страницы разных обновлений и закрывает доступ к оставшимся результатам

Место: `apps/web/src/hooks/useResultsWorkspace.ts:95–107`; отмена только при смене фильтра: `119–123`.

Обновление первой страницы не отменяет и не инвалидирует текущую дозагрузку того же фильтра. Поздняя страница старой выборки добавляется к обновлённой первой странице, затем заменяет актуальные `hasMoreResults`, `totalResults` и номер страницы.

Воспроизведение: ожидается старая страница 2 из 2 с общим количеством 200 → обновление первой страницы сообщает о 300 результатах и трёх страницах → приходит старая страница 2. Таблица смешивает две выборки, общее количество снова равно 200, `hasMoreResults=false`; страница 3 становится недоступной.

Исправление: связать дозагрузку с поколением основной выборки. При обновлении первой страницы отменять старую дозагрузку и сбрасывать её состояние; поздний ответ не должен менять ни строки, ни метаданные пагинации.

### 4. P2 — открытый результат возвращается в другую поисковую выборку

Место: `apps/web/src/hooks/useResultsWorkspace.ts:148–149, 170–177`.

Выбранный серверный результат сохраняется при смене фильтра. Если его нет в новой выборке, загрузчик деталей получает запись и связанные результаты и добавляет их непосредственно в список, не проверяя соответствие фильтру. Сохранение открытого просмотра полезно, но оно не должно менять состав поисковой выборки.

Воспроизведение: выбран результат по старому запросу → введён новый запрос → сервер вернул одну новую запись. После загрузки деталей список содержал новую и старую записи при серверном общем количестве 1. В API-режиме журнал повторно не фильтрует текст поиска на клиенте, поэтому старая запись отображается пользователю и участвует в сводке.

Исправление: хранить данные открытого просмотра отдельно от результатов поиска. Загрузка выбранного обхода или переход к нему по ID не должна подмешивать записи в отфильтрованный журнал и менять его счётчики.

### 5. P2 — текст комментария искажает состояние точки и сводку дашборда

Место: `apps/web/src/features/patrol/results/resultPresentation.ts:6–13`; использование для сводки: `apps/web/src/features/dashboard/dashboardSummary.ts:98–103`.

Общий классификатор ищет подстроки в комментарии и выдаёт им приоритет над явным состоянием. Комментарий «Неисправностей не обнаружено. Оборудование исправно.» при отсутствии замечания считается неисправностью. Комментарий «Неисправно. Запасной ключ недоступен.» при явном замечании «Повреждено крепление» превращает результат в «Метка недоступна».

Последствия: неправильные статусы в просмотре, фильтры и счётчики замечаний, экспорт и список проблемных точек дашборда. Оба примера воспроизведены на текущем классификаторе.

Исправление: состояние определять по структурированным полям результата; комментарий использовать для отображения. Совместимость со старыми данными должна иметь отдельное ограниченное правило только при отсутствии структурированного состояния.
