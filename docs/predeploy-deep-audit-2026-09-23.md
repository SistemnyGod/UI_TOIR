# Аудит перед обновлением сервера — 23 сентября 2026

## Решение

Текущую связку API / веб / мобильное приложение пока не считать принятой к рабочему выпуску. Серверные автоматические проверки проходят, но выявлены дефекты обновления мобильной базы, определения завершения, фильтрации и жизненного цикла списков. Есть отдельная проблема синхронизации обращений на сервере и небезопасная нормализация адреса на клиенте.

Продуктовый код не менялся. Добавлен только диагностический скрипт `tools/audit-predeploy-2026-09-23.cjs` и этот отчёт. Рабочая БД и развёрнутые сервисы не изменялись. Проверка не является доказательством отсутствия всех регрессий: телефоны, восстановление рабочего бэкапа, полная визуальная приёмка и нагрузочный прогон не выполнялись.

## Воспроизведения и найденные дефекты

### 1. P1 — обновление установленного приложения не добавляет refresh_mode

Места: `mobiel proekt/src/db/database.ts:405,427,516,639,1157`; чтение — `src/services/workTaskService.ts:64`.

Поле добавлено в уже существующие миграции `20260922_work_paging_and_drafts` и `20260922_work_refresh_state_recovery`. Нового маркера нет. Если оба старых маркера уже записаны, обновление пропускает ALTER TABLE. Проверка фактической функции `runLocalMigration` на SQLite воспроизводит `no such column: refresh_mode`.

Исправить: отдельная добавочная миграция поля, сохраняющая курсоры. Проверять полный путь запуска миграций на базе предыдущей редакции, а не только прямой вызов schema helper. Нынешний `workRefreshSchema.vitest.test.ts` вызывает helper напрямую и поэтому не покрывает пропуск по уже существующему маркеру.

### 2. P1 — недоказанное завершение считается готовым локальным отчётом

Места: `src/services/patrolNavigationService.ts:21–45`; `src/db/database.ts:460–480`; `src/features/patrol/SubmitReportScreen.tsx:58`.

Миграция намеренно оставляет неоднозначные записи с `local_report_present=1`, `local_report_needs_review=1`. `getPatrolReportState` не читает второй флаг. Для записи syncError без команды завершения возвращает `completedLocally=true`. Воспроизведено фактической функцией на SQLite. Дальше экран и восстановление после запуска используют это как факт отчёта.

Исправить: разделить «результаты доступны для проверки» и «доказано локальное завершение». Сохранить запись в журнале, но не выдавать её за завершённую и не блокировать явное завершение после проверки. Тестировать неоднозначную запись, обычную ошибку точки, действительное завершение и переоткрытие.

### 3. P1 — явный HTTPS-адрес преобразуется в HTTP

Места: `src/core/serverSettings.ts:145–148`; `src/core/environments.ts:11–17`; `src/api/httpClient.ts:233–248`; `infra/docker/Caddyfile:1,35`.

Фактическая функция `normalizeServerBaseUrl('https://192.168.2.194')` возвращает `http://192.168.2.194:5173`. Правило действует по имени узла, независимо от явно указанной схемы. В local-enterprise также разрешён внешний HTTP-кандидат. HTTP-запросы могут содержать Bearer-токен; Caddy сохраняет HTTP для совместимости, не перенаправляя его на HTTPS.

Это подтверждение поведения исходников, а не утверждение, что установленный APK сейчас использует внешний адрес. Проверки внешнего узла и отправки учётных данных в ходе аудита не было.

Исправить: не понижать явный HTTPS до HTTP; отдельно обрабатывать только устаревший HTTP-адрес. Для выпуска определить точный доверенный HTTPS origin и проверить сертификат на установленном APK. Внешний резервный адрес не включать автоматически в рабочий сценарий до отдельной приёмки. При отказе сертификата не обходить проверку TLS.

### 4. P2 — после возврата 75 работ снова превращаются в 25

Места: `src/features/emuTask/WorkAccountingScreen.tsx:179–189,533,577`.

reloadLocal читает `local:tasks:owner:contour:filter:employee`, подгрузка сохраняет `local:tasks:filter:employee`. Для замечаний аналогично. В диагностике вызваны реальные обработчики: две подгрузки дают 75 записей, возврат читает другой ключ и показывает 25. Данные в SQLite не удаляются; теряется достигнутый видимый диапазон.

Исправить: единый создатель контекста/ключа для чтения, сохранения и подгрузки. Отдельно сохранять якорь прокрутки. Проверять весь цикл «открыть → две страницы → уйти → вернуться», а не подставлять в тесте 75 для любого ключа.

### 5. P2 — фильтры «Доступные» и «История» всё ещё рассогласованы

Места: `WorkAccountingScreen.tsx:195,273–275,548,696,869`; `workTaskRepository.ts:141–175`; `workTaskService.ts:17–24`.

Для «Доступных» экран передаёт null вместо выбранного сотрудника. SQLite ограничивает общие активные работы, а исключение собственных выполняется после LIMIT в React. Первые 25 могут оказаться собственными, при этом подходящие работы находятся дальше. Кнопка продолжения скрыта при пустом отфильтрованном списке; автоматический onEndReached не заменяет надёжной явной подгрузки.

Если просто передать исполнителя в существующий SQL, появляется второй дефект: `NOT (employee_id = ? OR ...)` для неназначенной работы с NULL даёт NULL и исключает её. Это воспроизведено фактической функцией SQL-чтения.

Открытие «Истории» вызывает общий loadWorkItemsOfflineFirst, который обновляет active, а не history. История может обновиться только отдельной подгрузкой. React-проверка принадлежности также игнорирует employeeId и проверяет только массивы участников, в отличие от SQL.

Исправить: единый фильтр для локального и серверного запросов; NULL-безопасный предикат; обновление нужного раздела при открытии; доступные ошибка/повтор/продолжение даже при пустом результате. Проверить 25 собственных перед чужими, неназначенные записи и старый контракт участников.

### 6. P1 — поздние ответы замечаний применяются к новому списку

Места: `WorkAccountingScreen.tsx:274–286,523–542,583–587`.

Ветка замечаний после await не проверяет поколение вообще. Диагностика меняет поколение во время задержанного чтения: старый ответ всё равно вызывает setRemarks. При смене аккаунта это может показать строки прежнего аккаунта в новом экране; запись этих строк под другим владельцем этим тестом не проверялась и не утверждается.

Также `.then(() => reloadLocal(true))` после первоначальной загрузки не проверяет фокус; cleanup не инвалидирует поколение. loadingMore защищён React-state, а не синхронным владельцем операции; старый finally может снять индикатор новой загрузки.

Исправить: один фиксированный контекст аккаунта, контура, фильтра и фокуса на всю операцию. Инвалидировать при уходе/смене, проверять перед каждым изменением UI, освобождать блокировку только её владельцем. Синхронная защита повторного нажатия обязательна.

### 7. P2 — завершение обхода не продвигает время изменения обращения

Места: `libs/infrastructure/Persistence/MobileApp/EfMobileAppService.Outbox.Patrol.Completion.cs:212–219`; `EfMobileAppService.PatrolAppeals.cs:76–81,168`; `Patrol360DbContext.cs:8–17,202`.

По коду: при завершении обхода открытый запрос отмены становится obsolete, изменяются ответ, ResolvedAt и Version, но не UpdatedAt. API сортирует страницы по UpdatedAt. В SaveChanges нет общего обновления этого поля для обращений. Старое изменённое обращение остаётся на прежней глубокой странице, тогда как обычное обновление мобильного репозитория получает лишь начало. Клиент может продолжать показывать прежнее состояние.

Исправить: обновлять UpdatedAt в той же транзакции при каждом изменении обращения. Добавить PostgreSQL-регрессию: старое обращение за первой страницей → завершение обхода → оно появляется в странице изменений с новой версией. Этот конкретный сценарий в текущем аудите на PostgreSQL не воспроизводился; основание — проверенный путь записи и чтения кода.

### 8. P2 — обращения не имеют полноценного непрерывного обновления

Места: `src/db/repositories/patrolAppealRepository.ts:16–32,51–103`; `src/features/patrol/PatrolAppealScreen.tsx:22–32`.

По коду: нет прохода новых страниц до прежней границы ID/версии; старый сервер без фильтра прекращает поиск, найдя хотя бы одно обращение маршрута. Ошибка HTTP превращается в null, неотличимый от конца. Репозиторий не использует assertDataOwnerContext после сети, а экран не защищает setData сменой фокуса/назначения. Открытие экрана дополнительно инициирует общий refresh.

Исправить: отдельные локальное чтение / обновление начала / продолжение, сохранённый прогресс, фиксированный контекст сессии, явная ошибка и повтор. Это доработка доставки обращений, не реализация исключённой из этапа истории сообщений.

### 9. P2 — сохранение форм и владелец черновика не полностью соответствуют соглашению

Места: `WorkAccountingScreen.tsx:304–321,396–402`; `PointFillScreen.tsx:67–97,156–162`; `pointDraftController.ts:31–52`.

По коду: при редактировании и завершении работы владелец черновика берётся из task.employeeId, а не выбранного исполнителя устройства. Повтор навигации точки после ошибки перезаписывает первое сохранённое направление. На blur контроллер точки закрывается и отменяет таймер без flush в cleanup; usePreventRemove перехватывает удаление экрана, но не все способы потери фокуса. Последний случай требует проверки реальной навигации/таба, а не объявления доказанной потери текста на телефоне.

Исправить: фиксированный владелец формы; сохранение первого намерения перехода; единый контроллер перехода с разрешённым вводом и дождаться актуальной редакции. Добавить экранные тесты tab/Back/камера/ошибка/повтор и проверку на устройстве.

## Дополнительные риски и оптимизация

- Восстановление истории использует inProgressCursor даже при впервые обнаруженной повреждённой границе (`workTaskService.ts:72–93`). Следует отличать уже начатый recovery от недостоверного refresh: первый продолжать, второй начинать сначала. Новую потерю 15 записей этот аудит не утверждает.
- Обновление начала работ всё ещё вызывает listLocalWorkItems и читает все карточки с коррелированными счётчиками вложений ради границы ID/ревизия. Нужна компактная выборка границы.
- reloadLocal перечитывает работы, замечания, сотрудников и участки вместе; setTaskHasMore(true) повторно открывает уже проверенный конец. Событиям нужны ID затронутых объектов и состояние подтверждённого конца.
- isReportFullyDelivered делает отдельный SQL-запрос на каждый файл. Проверять файлы пакетом в согласованном контексте отчёта.
- Inventory chunk веба — 584,36 kB до gzip; сборка предупреждает о размере. Разделение загрузки экранов — направление оптимизации, не блокер целостности данных.
- Замеры батареи/памяти/времени сохранения и сравнение 100/1 000/10 000 команд в этом аудите не проводились. Ускорение не заявляется.

## Перед обновлением сервера

1. Исправить серверный UpdatedAt обращений и мобильные P1; закрепить дефекты полноценными регрессиями. Диагностический скрипт этого аудита подтверждает нынешние дефекты и намеренно НЕ является зелёной приёмкой исправленного поведения.
2. Согласовать фильтры, ключи диапазона, контекст запросов, черновики и непрерывность обращений. Отдельно проверить фактическую навигацию после офлайн-завершения.
3. Сформировать воспроизводимый набор исходников/образов. Рабочее дерево содержит большой набор изменённых и новых файлов; HEAD не идентифицирует текущую сборку. Сохранить manifest и image digests, старый набор API/worker/web.
4. Проверить обновление копии предыдущей серверной схемы и копии предыдущей мобильной базы. Успешное создание свежей тестовой PostgreSQL не заменяет восстановление и миграцию бэкапа.
5. Подтвердить бэкап и его восстановление, сохранность файлов и ключей. Миграция PatrolPausedAssignments меняет уникальный индекс и явно запрещает обратную миграцию при нескольких приостановленных обходах сотрудника. Откат нельзя обещать простым возвратом старого бинарника.
6. Повторить сборки и проверки, свежий аудит зависимостей; отдельно Gotenberg, внешние Excel-источники при их включении в выпуск. HTTPS/сертификат и настройки конкретного APK проверить на устройстве.
7. Пилот на двух телефонах: А не закончил → Б выбрал свою заявку → завершил офлайн → вложения/отчёт подтверждены → список → перезапуск не возвращает А. NFC, фото, Back, крупный шрифт, память и батарея пока не выполнены.

Compose уже отделяет мигратор от API и ожидает его успешное завершение; инициализатор использует advisory lock. Это полезные защиты, но они не заменяют предрелизную проверку бэкапа и контрактов. Сервер в этом аудите не обновлялся.
