## Подтверждённые дефекты

### B16 01 Снимок маршрута может содержать точки другой версии

**P1.** [Создание серверного снимка](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.RouteRevisions.cs:8>), [чтение маршрута при создании заявки](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.Requests.cs:114>), [параллельная мобильная реализация](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/MobileApp/EfMobileAppService.Helpers.cs:12>).

Маршрут и его точки читаются разными запросами. Транзакция создания заявки не защищает маршрут от параллельного редактирования. Между чтениями другой запрос может изменить точки и увеличить версию маршрута. В результате сохраняется неизменяемый снимок со старым `VersionNo` и новым содержимым точек. Concurrency token самого маршрута здесь не помогает: создание заявки маршрут не обновляет.

Воспроизведение на PostgreSQL: создание заявки прочитало маршрут v1; отдельный контекст изменил точку и сохранил маршрут v2; затем создание продолжилось. В БД получены маршрут v2 и снимок v1 с названием точки из v2. Это может нарушить согласованность полученного телефоном задания и последующего отчёта.

Исправление: единый сервис снимков для веба и мобильного пути; согласованное чтение версии и точек. Если выбран протокол блокировки, читать маршрут после захвата блокировки и применять тот же протокол ко всем изменениям маршрута. Дополнительно обработать одновременное создание одного снимка по уникальному ключу `(route_id, version_no)`. Формат мобильного контракта сохранять.

### B16 02 Два завершения работы ЭМУ принимаются с одной версией

**P1.** [Проверка версии и завершение](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Emu/EfEmuService.WorkSessions.Completion.cs:15>), [загрузка для изменения](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Emu/EfEmuService.Helpers.Loading.cs:61>), [модель версии](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol360DbContext.Emu.cs:194>).

`RowVersion` сравнивается с прочитанной сущностью, но не настроен как EF concurrency token. `LoadSessionForUpdate` выполняет обычное чтение. Завершение не использует блокировку `BeginActiveParticipationMutation`, применённую к созданию, добавлению участников и возобновлению работы.

Два запроса с `RowVersion=1` и разными комментариями одновременно прошли проверку и вернули успех. В БД осталась версия 2, а в истории — два события завершения. Один результат перезаписан, второй клиент не получил конфликта.

Исправление: атомарная проверка и изменение версии, единые правила блокировки/конкурентного обновления. Проверить совместно завершение, паузу, изменение участников, удаление, ручной и ночной перенос. В этом аудите параллельное воспроизведение выполнено именно для двух завершений; остальные перечисленные пары остаются сценариями для регрессионных тестов.

### B16 03 Настройка обязательного фото теряется при сохранении точки

**P2.** [Маршрут с точками](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.Routes.cs:114>), [добавление точки](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.Routes.cs:211>), [редактирование точки](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.Routes.cs:248>).

DTO и веб-формы передают `RequiresPhoto`, но сервис записывает `false`. Создание маршрута с `RequiresPhoto=true` и последующее редактирование с тем же значением успешно завершились, а в БД сохранилось `false`. Редактирование существующей точки также снимает ранее заданное требование.

Исправление: сохранять переданное значение во всех трёх путях, проверить DTO → БД → снимок → bootstrap. Значение по умолчанию оставить необязательным. Отдельно согласовать формулировку веб-переключателя с существующей политикой: мобильный сервер требует фото для проблемного/пропущенного результата при включённом требовании точки.

### B16 04 Групповая работа завершается раньше прихода части участников

**P2.** [Проверка времени окончания](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Emu/EfEmuService.WorkSessions.Completion.cs:65>).

Проверяется время прихода самого раннего участника через `Min`. Пример: один пришёл в 08:00, другой — в 10:00; окончание 09:00 принимается для обоих. Проверка на PostgreSQL подтвердила сохранённое `FinishedAt < ArrivedAt` у второго участника. Последующий расчёт обнуляет отрицательную длительность, но не исправляет противоречащие друг другу даты.

Исправление: проверять границы времени каждого завершаемого участника; при групповом окончании оно не может быть раньше самого позднего прихода. Дополнить проверками частичного завершения и разных времён присоединения.

### B16 05 Завершение и интервалы участия сохраняются раздельно

**P2.** [Раздельные операции записи](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Emu/EfEmuService.WorkSessions.Completion.cs:124>), [закрытие интервалов](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Emu/EfEmuService.Helpers.WorkSessions.cs:109>).

Сначала `SaveChanges` фиксирует завершение работы, участников и аудит, затем отдельный `ExecuteUpdate` закрывает интервалы. Общей транзакции нет. Воспроизведение с искусственным отказом второго SQL-запроса: метод завершился исключением, но карточка уже завершена, а интервал остался открытым. Повтор с прежней версией не является надёжным восстановлением частично выполненной операции.

Исправление: одна транзакция для состояния работы, участников, интервалов, связанного плана и аудита. Проверить аналогичные последовательности в паузе и завершении участия. Не выполнять массовое исправление старых интервалов без отдельной диагностики фактических данных.

## Оптимизация и структура

1. **Убрать поштучные проверки точек при сохранении веб-отчёта.** [UpsertPatrolPointResults](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/Patrol/EfPatrolStore.Results.cs:124>) вызывает `RoutePoints.Any` внутри цикла. Диагностический тест с 54 точками подтвердил 54 отдельных `SELECT EXISTS` только для этой проверки. Один запрос существующих ID и локальный `HashSet` сохранят смысл проверки, включая удалённые точки старого снимка. Время ускорения на рабочей нагрузке не измерялось.
2. **Не собирать все страницы справочников внутри одного HTTP-запроса.** [Inventory options](<C:/Users/AI_server/Desktop/Proekt obhod/apps/api/Controllers/InventoryController.cs:93>) загружает сотрудников и товары целиком, местами также старую сводку остатков. [LoadAllPages](<C:/Users/AI_server/Desktop/Proekt obhod/apps/api/Controllers/InventoryController.cs:907>) отменяет пользу серверной пагинации для этих ответов. Переводить активных потребителей на поиск и страницы; старый endpoint сохранять на переходный период. Это кандидат на нагрузочное измерение, а не доказанная задержка конкретного пользователя.
3. **Разделить обязанности, а не только partial-файлы.** `EfPatrolStore` обслуживает маршруты, сотрудников, мобильные аккаунты, заявки, назначения и дашборд через один DbContext. Сервис Inventory объединяет выдачу, карточки, нормы и документы. Начать с общих правил снимков и команд ЭМУ, затем выделять сервисы по сценариям с явной границей транзакции.
4. **Согласовать пути вложений.** [Мобильная загрузка](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Persistence/MobileApp/EfMobileAppService.Files.cs:103>) и readiness используют `AppContext.BaseDirectory/mobile-files`, а [LocalAttachmentStore](<C:/Users/AI_server/Desktop/Proekt obhod/libs/infrastructure/Attachments/LocalAttachmentStore.cs:12>) поддерживает `Patrol:AttachmentStoragePath`. Сейчас это два механизма. Объединять с сохранением чтения старых файлов; проверить отказ/отмену во время записи `.uploading`. Метод `DeleteStaleStagedFiles` существует, но вызовов из API/worker/tools не найдено. Отсутствие файловой уборки требует отдельного решения; удалять файлы без сверки с БД нельзя.
5. **Измерить глобальные блокировки.** ЭМУ сериализует некоторые операции общей блокировкой участия; ПЕРКО — изменения присутствия. Это полезные гарантии целостности. Сначала собирать ожидание блокировки, длительность и число обработанных строк; уменьшать область только при сохранении бизнес-инвариантов. Не снимать блокировку ради формального ускорения.
6. **Ограничить рост bootstrap без удаления действующих назначений.** Пилотные маршруты всё ещё заданы именами `Обход печей` и `Помол`; часть старого bootstrap собирает массивы и курсор в памяти. Следующий шаг — явные настройки доступных маршрутов и измерение размера ответа, времени SQL и сериализации на большой базе. Добавление пагинации — только с согласованной поддержкой старых APK.
7. **Дополнить эксплуатационные метрики.** Есть heartbeat worker по push/ПЕРКО/ЭМУ и проверки readiness. Для диагностики задержек нужны сквозные ID заявки/назначения/операции, возраст очереди, повторные попытки и время приёма отчёта. Пароли и токены в журналы не добавлять.
8. **Убрать противоречия документации.** `docs/structure-remaining-work.md` описывает состояние от 18 мая, включая прежний каталог прототипа и условную оценку 89%. Это не актуальная оценка готовности. Основной статус должен ссылаться на текущие сценарии, проверки и открытые дефекты.

Индексы без измерений на характерном объёме данных не предлагались. В этом аудите подтверждено число лишних запросов, но не выполнен нагрузочный прогон рабочей базы и не получены её планы `EXPLAIN ANALYZE`.
