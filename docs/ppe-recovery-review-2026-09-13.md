# СИЗ: восстановление рабочего процесса

Проверка 13.09.2026. Изучены текущий диалог, связанные задачи «Аудит производительности» (рабочая копия 556a) и «Изучить проект», действующий frontend, маршруты выдачи, серверная печать, отчёты предыдущих аудитов и документация отдельного конструктора. На рабочем сервере открыт экран СИЗ без создания или изменения данных. Это диагностика, не акт приёмки всего модуля.

## Главный вывод

Нужно довести и интегрировать уже созданный документ выдачи, а не создавать ещё один вариант интерфейса. В основном checkout нет PpeIssueDocumentConstructor и API issue-documents. Они существуют в незакоммиченных изменениях отдельной копии 556a. В ней новый процесс дополнительно выключен флагом по умолчанию. На рабочем сервере виден старый экран. Точное соответствие серверных бинарных файлов checkout в этом проходе не установлено.

## Подтверждённые наблюдения

1. Рабочий экран загружает сотрудников и карточку, поэтому общий отказ загрузки не воспроизведён. У открытой карточки отображается отсутствие опубликованной нормы. Это не доказательство отсутствия норм у всех сотрудников.
2. Экран одновременно показывает сопоставленные строки и подпись «Связь с товаром ещё не задана». В InventoryPpeScreen.tsx подпись выбирается по brandModelArticle/mappings.length, тогда как счётчик сопоставления использует mappedItemId. Отсутствие реквизитов товара ошибочно представлено как отсутствие связи.
3. Открытие выдачи ищет уже связанный товар по названию среди первых 30 результатов (InventoryPpeScreen.tsx, openIssue), затем сравнивает ID. При переименовании или большом числе одноимённых товаров связь может не разрешиться. Отдельной обработки исключения в openIssue нет; окно открывается только после завершения запроса. Следует читать товар по ID и показывать ошибку с повтором.
4. Текущий PpeIssueWorkflowScreen сохраняет выдачу через createPpeIssueBatch(draft.id), а скачивание — через printPpeCard(draft.id). Это маршрут карточки, а не самостоятельного документа выдачи. Скачать файл можно только после committed. Он отличается от согласованного сценария предварительной печати без создания факта.
5. Серверная печать карточки использует отдельные реализации DOCX и PDF. PDF уходит в SimplePdfBuilder: одна страница, lines.Take(52), ASCII/WinAnsi. Это не полноценная многостраничная русская форма. В DOCX-подготовке также осталось подставляемое основание «п. 1645 Приложения № 1». Такие значения нельзя принимать за проверенную норму.

## Что уже сделано в 556a

По коду и docs/ppe-issue-documents.md: отдельная сущность документа, API, версии, черновик/подтверждение, снимки данных, отдельные строки, печать, права управления нормами и добавочная миграция. По отчёту предыдущей задачи выполнены 34 новых серверных теста, 70 API-тестов, импорт 448 строк/34 блоков и браузерный сценарий с synthetic API. Эти результаты в данном проходе заново не запускались.

Оставшиеся ограничения из того же отчёта: настоящий Gotenberg не проверен из-за ошибки получения образа; общий регрессионный прогон не был зелёным; браузерная проверка не использовала настоящий API пилота. Поэтому утверждение «реализовано» не означает «работает на сервере».

## Рекомендуемый путь

1. Зафиксировать и сохранить обе рабочие копии. Сравнить изменения 556a с текущими исправлениями стабилизации и адаптивности; интегрировать только СИЗ в отдельную ветку, не копировать worktree поверх проекта.
2. Зафиксировать один пользовательский процесс: сотрудник → опубликованная применимая норма → выбранные товары → количество/размер/цена/даты → проверка → предварительные Word/PDF → отдельное подтверждение. Постоянная карточка и история сохраняются отдельно.
3. Исправить диагностические подписи и загрузку товара по ID. Отдельно показывать: нет нормы, норма не опубликована, не выбран товар, не подтверждено соответствие, нет цены, ошибка сети. Каждый блокирующий статус должен вести к конкретному действию.
4. Поднять изолированный API/PostgreSQL/Gotenberg. Проверить миграции на пустой БД и тестовой копии со старыми карточками/черновиками. Спорные связи не утверждать автоматически.
5. Пройти реальный сквозной сценарий через web и API: выбор нормы, несколько вещей под одной нормой, разные даты, автосохранение, повторное открытие, печать обеих форм, подтверждение, повтор запроса без дубля, история. Складских движений быть не должно.
6. Сверить DOCX/PDF на длинных русских названиях и многостраничных таблицах. Ошибка PDF не должна блокировать DOCX или сохранение.
7. Только после этого — отдельный пилот и согласованное рабочее включение. До приёмки не объявлять модуль готовым по одному build или mock-тестам.

## Критерий готовности

Бухгалтер самостоятельно оформляет выдачу от выбора сотрудника до двух корректных документов и видит подтверждённую выдачу в истории после перезапуска. Повторное подтверждение не создаёт дублей, справочники не меняют старые документы, телефон и desktop позволяют заполнить все поля. Конкретный сообщённый пользователем сбой должен быть воспроизведён и закрыт отдельным регрессионным сценарием.

В этом проходе исходники приложения и рабочие данные не изменялись; создан только этот отчёт. Выдача и подтверждение на рабочем сервере не выполнялись. Не утверждается, что изучены все исторические сообщения каждого чата или заново проверены все прежние находки.
