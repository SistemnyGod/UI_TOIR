# Оптимизация Patrol360 — 8 сентября 2026

Этап реализует оптимизацию путей данных для целевого сценария из 50 web- и 50 Android-клиентов. Рабочий сервер, телефоны и worktree `556a` не переключались.

## Реализовано

- Списки работ, изменений, истории, dashboard и замечаний ЭМУ получают подтверждённые вложения одним запросом на страницу, а не запросом на DTO. Пустые выборки не обращаются к `mobile_uploaded_files`.
- Проверенный bearer-пользователь хранится только в scoped-контексте HTTP-запроса. Контроллеры повторно его не читают; следующий запрос по-прежнему проверяет отзыв сессии и права.
- PERCo хранит durable-очередь сотрудников для пересчёта. События и перепривязки атомарно ставят в неё прежнего и нового сотрудника; обычный цикл пересчитывает полную историю только этих сотрудников. Полный пересчёт остался recovery-путём.
- Дедупликация входящей страницы PERCo ищет только кандидаты этой страницы, без загрузки всех идентификаторов и естественных ключей истории в память.
- Worker heartbeat и API diagnostics показывают очередь, возраст, обработанных сотрудников/событий/интервалов, длительность и ожидание advisory lock.
- Web загружает dashboard, сотрудников и маршруты по потребности экрана. GET-кеш текущей сессии живёт 60 секунд, объединяет одинаковые запросы, сбрасывается при командах/refresh/смене пользователя, прав или режима; устаревший ответ не применяется.
- Добавлен изолированный performance toolkit: сидер с 1 000 сотрудниками и 1 000 000 событий PERCo, metadata 20 000 ЭМУ-вложений, EXPLAIN для целевых запросов, k6-сценарий 50+50 и сбор runtime метрик PostgreSQL/Docker.

## Нагрузка

Инструменты находятся в `tools/performance/`, запуск описан в `tools/performance/README.md`. Целевая нагрузка намеренно не запускалась на текущей машине: нет k6, 50 изолированных web-токенов, 50 мобильных акторов с назначенными работами и контролируемых PERCo/push-провайдеров. Поэтому p95/p99 и показатели CPU/RAM не заявляются как достигнутые.

Перед измерением создать отдельный `patrol360_perf_*`, применить миграции, выполнить сидер, подготовить файл конфигурации вне Git и трижды запустить k6 вместе с `Collect-PerformanceMetrics.ps1`. Только результаты этих трёх одинаковых прогонов можно сравнивать с целями 100-клиентного этапа.

Новые Release-артефакты и их хэши сохраняются в `artifacts/optimization/`. Они описывают внутренний кандидат; обязательные ворота предыдущей стабилизации — mobile dependency advisories, новый подписанный APK, физический Android, доверие HTTPS и восстановление резервной копии — остаются незавершёнными.
