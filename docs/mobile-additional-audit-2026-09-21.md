# Дополнительный аудит мобильных обходов — 21 сентября 2026

Аудит после рефакторинга, описанного в `mobile-review-refactor-2026-09-21.md`. Проверены взаимодействия локального состояния, bootstrap, отмены, переключения, истории отчётов и индикатора связи. Код приложения и сервера в этом аудите не менялся. Добавлены этот отчёт и воспроизводящий диагностический скрипт.

## Подтверждённые проблемы

### 1. P1 — Отчёт с конфликтом исчезает из журнала после bootstrap

**Место:** `mobiel proekt/src/db/repositories/bootstrapRepository.ts:1117–1120`; зависимый фильтр — `patrolReportRepository.ts:39`.

Сценарий: обход завершён локально, сервер вернул конфликт, локальный статус стал `needsDispatcherDecision`. В следующем применённом bootstrap серверный обход ещё `inProgress`, его дата завершения пустая. Upsert сохраняет локальный статус конфликта, но дату `completed_at_local` сохраняет только для статуса `completedLocal`. В результате дата становится NULL, а журнал отбирает локальные отчёты именно по непустой дате.

**Воспроизведение:** исходный SQL приложения выполнен в SQLite в памяти. До bootstrap в журнале одна запись, после — ноль; статус остаётся `needsDispatcherDecision`. Это исчезновение доступа из журнала, а не доказательство удаления результатов точек.

**Исправление:** отделить сохранённый локальный итог от изменяемого статуса назначения. Сохранять дату/снимок незавершённой доставки при bootstrap; сбрасывать их только явным действием переоткрытия отчёта. Проверить конфликт, ошибку доставки, авторизацию и отмену.

### 2. P1 — Отмена не учитывает исходный маршрут ожидающего переключения

**Место:** `mobiel proekt/src/db/repositories/patrolCancellationPolicy.ts:18–20`; обработчик — `patrolCancellationRepository.ts`.

Переключение A → B хранится как команда назначения B с `sourceAssignmentId=A`. При отмене A функция поиска связанных команд проверяет только `entityLocalId`, `entityServerId` и `payload.assignmentId`. Исходный маршрут не учитывается.

**Воспроизведение:** реальная функция возвращает пустой список для A и команду переключения для B. Следовательно, отмена A оставляет ожидающую команду A → B в очереди. Дальнейший конфликт этой команды на сервере способен заблокировать B, хотя отменён A. Последнее следствие подтверждено чтением серверной проверки и локального обработчика конфликтов; полный сценарий двух телефонов не запускался.

**Исправление:** учитывать обе стороны переключения и выполнять явное согласование двух назначений и зависимостей. Простого добавления `sourceAssignmentId` в фильтр недостаточно: нужно определить судьбу уже заполненных точек B и последующих команд. Нужны сценарии отмены A/B до отправки, после приёма сервером и при потере ответа.

### 3. P2 — Приостановленный маршрут не принимает серверное возобновление

**Место:** `mobiel proekt/src/domain/sync/bootstrapResolutionPolicy.ts:41–44`.

Пауза имеет ранг выше выполнения, поэтому `resolveBootstrapAssignmentStatus('paused', 'inProgress', false)` возвращает `paused` даже без ожидающих локальных команд. Телефон остаётся в паузе после возобновления с другого устройства.

**Воспроизведение:** вызов исходной функции возвращает `paused` вместо `inProgress`.

**Исправление:** пауза и возобновление — обратимые переходы. Согласовывать их по версии и наличию локальных команд; не применять к ним линейный порядок прогресса. Проверить два устройства, A → B → A и запоздалые bootstrap.

### 4. P2 — После возврата в журнал «Загрузить ещё» повторяет старые страницы

**Место:** `mobiel proekt/src/features/patrol/usePatrolReports.ts:47–50`.

После загрузки 75 отчётов уход и возврат на экран запускают refresh первой страницы. Видимые 75 записей остаются, но курсор продолжения заменяется курсором после первых 25. Следующее нажатие загружает вторую, уже закешированную страницу, и видимый список не увеличивается.

**Воспроизведение:** выполнен код хука с детерминированными заменами React hooks и репозитория. Запросы страниц: `1, 2, 3, 1, 2`; после «Загрузить ещё» осталось 75 записей вместо 100. Это проверка управления загрузкой, не визуальный тест React Native.

**Исправление:** раздельно хранить границу обновления начала списка и курсор старой истории; не сбрасывать продолжение уже загруженного диапазона. Тестировать возврат на экран, ручное обновление, новые серверные записи и ошибку запроса.

### 5. P2 — Запоздалый успех API перекрывает подтверждённый офлайн

**Место:** `mobiel proekt/src/core/connectionMonitor.ts:29–34`.

После `setNetwork(false)` событие `outcome('connected')` безусловно выставляет `connected`. Оно может прийти от запроса, ответ которого получен раньше, а разбор завершился уже после отключения. Пока сеть остаётся отключённой, `check()` ничего не делает, и ложный статус может сохраняться.

**Воспроизведение:** исходный ConnectionMonitor после последовательности «успех → потеря сети → запоздалый успех» возвращает `connected`.

**Исправление:** учитывать поколение сети/адреса при публикации результатов запросов; при известном отсутствии сети отображать офлайн. Проверить также ответы старого адреса после смены настроек.

## Дополнительные замечания по оптимизации

- `EfMobileAppService.Bootstrap.cs:86–94` загружает всю историю обращений аккаунта, связанные назначения, сериализует все обращения и хеширует их при каждом bootstrap. С ростом истории растут ответ, серверная работа и локальные upsert. Нужны изменения после курсора, отдельная история с пагинацией и стабильная версия изменений. Абсолютное время и память не измерялись.
- Подписки невидимых экранов устранены не везде: `PatrolAppealScreen`, `PatrolRequestScreen`, `ActivePatrolScreen`, `SubmitReportScreen` ещё используют обычный `useEffect` для событий синхронизации. Экран обращений реагирует на каждое событие. Если экран остаётся смонтированным в стеке, продолжаются чтения БД. Нужны подписки по фокусу, фильтрация событий и защита от пересечения загрузок.
- В `bootstrapRepository.ts` и `outboxRepository.ts` существуют два разных механизма смены ID назначения. Второй переносит `sourceAssignmentId` переключения, первый — только `assignmentId`. Контекст SecureStore также не входит в этот перенос. Перед дальнейшим расширением сценариев стоит объединить перенос в одну транзакционную реализацию с проверкой всех ссылок.

## Прежние незакрытые вопросы

Полный путь разрешения конфликта отмены с офлайн-отчётом по-прежнему отсутствует. Ответ диспетчера всё ещё хранится в одном изменяемом поле Reply. Общий deadline обычного API-запроса с резервными адресами и refresh токена не введён. Эти пункты не считаются новыми находками и не закрыты предыдущими тестами.

## Проверки и воспроизведение

Команда: `node tools/audit-mobile-additional.mjs` из корня проекта.

Скрипт читает текущие исходники и исполняет их чистые функции, исходный SQL bootstrap/журнала в SQLite в памяти и код управления загрузкой с тестовыми заменами зависимостей. **Все пять описанных отклонений воспроизведены.** JSON сохранён в `TestResults/mobile-additional-audit.json`. `reproduced: true` означает воспроизведение ошибки, а не успешную приёмку функции.

Полный verify и серверные интеграционные тесты в этой итерации повторно не запускались: код приложения не менялся. Ранее прошедшие 173 мобильных и 7 серверных тестов не покрывают перечисленные комбинации событий. NFC, батарея, физические телефоны и визуальная приёмка в этом аудите не проверялись.

## Очерёдность исправления

1. Сохранность локального итога при bootstrap и отмене.
2. Переключение как единая операция двух назначений: отмена, перенос ID, согласование паузы/возобновления.
3. Курсор истории и актуальность индикатора связи.
4. Полноценные материалы конфликта и переписка, затем ограничение объёма bootstrap.
5. Сквозные проверки на двух телефонах и замеры на фиксированном наборе данных.
