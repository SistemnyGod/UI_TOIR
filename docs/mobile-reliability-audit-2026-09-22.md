# Аудит мобильных обходов — 22 сентября 2026

Проверен текущий рабочий код мобильного приложения и связанные контракты сервера. Код приложения не изменён. Добавлен диагностический скрипт `tools/audit-mobile-reliability-2026-09-22.mjs`, исполняющий функции приложения, фактические SQL-запросы и hook журнала с тестовыми зависимостями. База SQLite — только в памяти. Это проверки логики, не сквозная приёмка на устройстве.

## Вывод

Предыдущее заявление о полном выполнении плана было преждевременным. Базовый интерфейс, локальное хранение и очередь работают как основа, но критические сочетания отмены, переключения и доставки ещё не закрыты. Успешные прошлые 179 мобильных тестов не доказывают выполнение перечисленных ниже сценариев.

## Подтверждённые проблемы

1. **P1: отмена снимает ожидание переключения с неизвестным результатом.** `patrolCancellationRepository.ts:59` выбирает также отправляемые команды, затем переводит их в `superseded`. После расширения поиска на `sourceAssignmentId` отмена A затрагивает switch A→B. Результат операции на сервере до этого не выясняется. Зависимые команды B считают `superseded` разрешённой зависимостью и могут уйти раньше подтверждённого запуска. Кнопка продолжения доступна только для `conflict/rejected`, поэтому в этой ветке не помогает. Воспроизведение: switch в `sending` после отмены A становится `superseded`.

2. **P1: «Продолжить B» создаёт запуск после результатов B.** `patrolSwitchRepository.ts:145`, `outboxSql.ts:23`, `outboxRepository.ts:76`. Команда вставляется с MAX(sequence_no)+1, а обход switch-barrier не обходит последовательность агрегата. После снятия старого барьера сначала выбирается результат B, затем запуск. Сервер может отклонить результат и заблокировать последующий запуск. Воспроизведение реального SQL очереди возвращает `result-b`, а не `continue-b`. Нужны транзакционное размещение запуска перед неотправленными зависимыми командами и сохранение неизменности уже отправленных.

3. **P1: старые версии Bootstrap принимаются.** `bootstrapRepository.ts:1232` безусловно присваивает `revision = excluded.revision`; политика статусов не принимает версии. SQL-воспроизведение заменяет ревизию 10 ревизией 2. В дополнение, проверка незавершённых команд в строке 35 не включает `waiting_auth/waiting_network/blocked`, поэтому локальное намерение может считаться отсутствующим. Исправление: согласовывать версии до применения состояния, учитывать все реально ожидающие команды.

4. **P2: обновление начала журнала оставляет разрыв.** `usePatrolReports.ts:46` обновляет только одну страницу, сохраняя прежний курсор старой истории. После 75 загруженных отчётов и появления 40 новых загружаются 25 новых, а 15 остаются между новым началом и прежним курсором. Проверка фактического hook подтверждает отсутствие этих 15 записей в кеше. Также `limit` увеличивается до успешного запроса; признак remoteHasMore после возврата восстанавливается через номер страницы даже для исчерпанной истории. Нужно обновлять начало до пересечения с известными ID и отдельно хранить достигнутую границу.

5. **P2: отчёт без даты остаётся невидимым.** `patrolReportRepository.ts:40` требует `completed_at_local IS NOT NULL`. Надпись «Дата не указана» в UI не помогает локальному отчёту, отфильтрованному SQL. Воспроизведение: назначение `completedLocal` без даты отсутствует в журнале. Нужен отдельный устойчивый признак локального завершения/снимок отчёта; неизвестную дату оставлять пустой.

6. **P2: поздний успех может снять требование входа.** `connectionMonitor.ts:39` принимает connected того же поколения и сбрасывает authRequired. `connectionStatus.ts:26` не меняет общее поколение на смене сети; `httpClient.ts:51` меняет только отдельный authEpoch при входе/выходе. После обнаружения проблемы авторизации ответ ранее начатого API-запроса возвращает «На связи». Проверка монитора это воспроизводит. Прямой сценарий ответа при сохраняющемся offline уже защищён; проблема относится к авторизации и смене контекста. Нужен единый контекст сети/сервера/авторизации вне жизненного цикла React-подписчиков.

## Неполная реализация, установленная чтением кода

- **Обращения:** серверный курсорный API существует, но оба вызывающих места `refreshPatrolAppealsPage()` передают пустой курсор и игнорируют nextCursor. За первыми 25 изменёнными обращениями нет доступной загрузки. Открытие обращения старого маршрута также запрашивает общую первую страницу. В режиме без полного bootstrap часть обращений и решений может не попасть на телефон. Обновление обращений отдельно не публикует соответствующее событие UI. Нужны догрузка до сохранённой границы, локальный курсор, адресное обновление экрана.
- **Перенос ID остаётся двумя реализациями.** В outbox переносит `patrol_appeals`, в bootstrap — нет. Повторяющиеся блоки кешей и JSON допускают дальнейшее расхождение. Нужен единый транзакционный перенос с тестом всех ссылок, включая обе стороны переключения, обращения и выбранный маршрут.
- **Полноценное разрешение отмены против офлайн-отчёта** по-прежнему отдельная незакрытая задача: сохранение материалов конфликта и два реальных решения диспетчера.
- **История переписки** отсутствует как история сообщений внутри обращения. Новые сообщения создаются отдельными обращениями, а reply остаётся одним полем. Это не реализация полноценного диалога.
- **Общий deadline обычной API-операции** отсутствует. Ограничение проверки соединения не ограничивает суммарное время health, резервных адресов, запроса, refresh и повторного запроса. Это ранее выделенная отдельная задача.
- **Серверные подробности отчёта** пока показывают название точки, состояние, комментарий и число фото. Полноценного просмотра вложений и отображения причины ручного осмотра в этом экране нет.
- **Общее меню обхода** не выделено: ActivePatrolScreen и ScanNfcScreen отдельно формируют actions. Есть семантическое расхождение: ActivePatrolScreen:426 подписывает skipped как «Метка недоступна», хотя согласованный смысл — «Осмотр невозможен».

## Оптимизация и рефакторинг

1. Сначала исправить причинную последовательность очереди; микропроизводительность здесь вторична. Вынести общую логику зависимостей двух назначений, их переноса и согласования версий.
2. Сделать репозиторий обращений единым владельцем запросов: объединение параллельных загрузок, курсор, защита от устаревшего аккаунта и результата, отдельное событие изменений. Сейчас открытие экрана запускает прямой запрос и общий refresh; новое событие может вызвать ещё один прямой запрос.
3. Сохранить виртуализацию журнала: `PatrolReportsScreen` уже использует ScreenList/FlatList. Список обращений всё ещё строится через map внутри ScrollView; после исправления пагинации перевести его на виртуализированный список.
4. Кешировать статусы доставки только затронутых отчётов. Сейчас при обновлении перечитывается история команд для всех видимых локальных отчётов. Оптимизацию SQL/индексов выполнять после EXPLAIN и измерений на реалистичном объёме.
5. Убрать дублирование меню и модели итогов между экранами; унифицировать подписи ручного и невозможного осмотра.
6. Заменить критичные проверки текста исходников и моки enqueue сценарными тестами фактической очереди/SQLite. Старый диагностический скрипт проверяет обнаружение switch при отмене, но не последствия superseded; тест «Продолжить B» проверяет аргументы enqueue, но не порядок отправки.

## Рекомендуемый порядок

Отмена/неизвестный результат → порядок «Продолжить B» → версии и ожидающие команды → сохранность/видимость отчётов → непрерывная история и обращения → контекст связи → UI и измерения.

Приёмка: добавлять регрессионные тесты на последовательности событий, затем полный verify и серверные интеграционные проверки. После этого — два телефона общего аккаунта, NFC, офлайн-перезапуск, фото, малый экран/крупный шрифт. Аппаратная и визуальная приёмка в этом аудите не выполнялась. Показатели батареи, памяти и времени экранов не измерялись; численные обещания ускорения не делаются. Рабочее развёртывание не выполнялось.
