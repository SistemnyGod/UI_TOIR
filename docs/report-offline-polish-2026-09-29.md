# Сводка отчёта и восстановление отправки

29 сентября 2026. Доработки после APK 0.1.43; новый APK в этом проходе не собирался. Сервер, контракты, SQLite и правила фотографий не менялись.

## Экран отчёта

- Счётчик «X из Y» перенесён в строку названия маршрута. У счётчика нет переноса под название, длинное название может переноситься внутри своей области.
- Для готового, ещё не поставленного в очередь отчёта — одна строка «Всё готово к отправке отчёта». Подробная статистика осталась раскрываемой, её показатели не изменены.
- Значок облака справа открывает очередь сразу. Промежуточное меню убрано.
- Состояния после локального завершения, ошибки входа/сервера и ожидание вложений сохраняют свои сообщения. Готовность не приравнивается к подтверждённой доставке.

## Подтверждённые исправления отправки

1. Возвращение сети во время уже выполнявшегося цикла восстановления раньше терялось: новый вызов просто получал promise старой попытки. Регрессия получила только `normal`, хотя ожидался последующий `networkRecovered`. Теперь сохраняется признак повторного подключения и выполняется один последовательный дополнительный проход до обновления списков. Серия из 20 переключений сети объединяется; параллельной отправки из этих событий нет.
2. Повторная подписка на состояние сети сохраняла старое `lastNetworkUsable=true`, поэтому её начальное online-состояние не запускало очередь. Состояние подписки теперь инициализируется заново.
3. Повторные запросы объединяются только в пределах поколения сессии. Старый цикл после смены аккаунта не запускает последующие шаги и не освобождает блокировку нового цикла.
4. На экране очереди у единственного отчёта `waiting_network` без файлов отсутствовала кнопка ручной отправки. Она возвращена. Два быстрых нажатия раньше давали два вызова контроллера; теперь синхронная блокировка допускает один вызов и снимается после завершения/ошибки. Это не утверждение о создании двух серверных отчётов: нижний уровень уже имел собственные защиты.

## Проверки

В `output/report-offline-polish-20260929/` сохранены исходные падения и результаты после исправлений:

- `recovery-before-native.log`: 2 воспроизведённые ошибки, 2 успешных сценария.
- `queue-before.log`: отсутствует действие для ожидающего сети отчёта.
- `queue-double-before.log`: два вызова вместо одного.
- `vitest-all.log`: 256 тестов прошли.
- `node-tests.log`: 101 тест прошёл.
- TypeScript и проверка кодировки прошли.
- ESLint приложения и изменённых новых тестов: `lint-product.log`. Дополнительный запуск по всем старым тестам (`lint.log`) показал 50 предупреждений, без ошибок; массовое форматирование существующих тестов не выполнялось.

Стандартный запуск Vitest в этой сессии упёрся в запрет дочернего процесса, а автоматическая проверка расширенного разрешения дважды завершилась по тайм-ауту. Те же тесты успешно запущены внутри обычных разрешений с `--configLoader native --pool threads`; Node-тесты — с `--test-isolation=none`. Набор тестов не сокращён. Это эквивалентные этапы verify, не утверждение об успешном выполнении исходной команды `npm run verify` в неизменном окружении.

Новые проверки импортируют фактические контроллеры и монтируют экраны, а сеть/SQLite-границы управляются тестовыми заменами:

- сохранение завершения возвращает прежний ID и не ждёт сети;
- ошибка SQLite не запускает отправку и не сообщает об успешном сохранении;
- недоступная сеть не отменяет уже сохранённый отчёт;
- повторное подключение запускает доставку до скачивания списков;
- повторные online-события, сетевой дребезг, ошибка и повтор, смена поколения аккаунта;
- ручной повтор очереди после офлайн-ожидания, двойное нажатие;
- прежние проверки повреждённого отчёта, обязательных фото, поздней квитанции и просмотра истории остаются зелёными.

## Что это означает для телефона

Отчёт сохраняется на устройстве и отправляется автоматически после восстановления соединения, когда работает обработчик состояния сети приложения. Возвращение сети теперь не теряется за предыдущей попыткой. Фоновая задача также существует, но мгновенная доставка при полностью закрытом/остановленном приложении на физическом телефоне этим проходом не доказана.

Не измерялись фактическая скорость Wi-Fi, время TLS-подключения и доставка через нестабильную сеть телефона. Не выполнялась новая визуальная приёмка установленного APK. Для заявления о стабильности всего пути нужны физические проверки с фотографиями и потерей соединения; успешные управляемые тесты не заменяют их.
